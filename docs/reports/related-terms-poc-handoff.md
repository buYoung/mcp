# 유의어 데이터셋 PoC 작업 이력 인수인계

> **후속 (2026-10-08):** 사용자 승인으로 작업을 재개해 기능 PoC와 held-out 평가까지 마쳤다. 결과와 판정은 [관련 검색어 기능 PoC 결과 보고서](related-terms-feature-poc-report.md)를 보고, 이어진 반복 개선 3회(heldout-2~4)는 [3라운드 보고서](related-terms-feature-poc-round3-report.md)를, 평가를 다시 설계한 heldout-5는 [4라운드 보고서](related-terms-feature-poc-round4-report.md)를 본다. **최종 결정(2026-10-08): 관련 검색어 블록을 접는다.** 효과가 네 라운드 모두 기준에 못 미쳐 `initial_instructions`에 넣지 않고, 결과는 기록으로만 남긴다. 아래 4절의 마지막 `package.json` 오류는 같은 시각 `bun update`로 `package.json`이 실제로 바뀐 외부 변경이었고, 사용자 결정에 따라 판정 대상에서 제외했다. 아래 본문은 중단 시점의 이력으로 그대로 둔다.

> **현재 상태: 사용자 지시에 따라 중단.** 개발용 사전 구축과 새 평가 라벨 159개 수집까지 완료했지만, 제출 라벨의 최종 독립 검증에서 오류가 발생했다. 의미 품질 집계와 최종 보고서는 작성하지 않았다. 이 문서는 기존 작업 이력을 정리한 것이며, 작업 재개나 오류 진단을 승인하는 문서가 아니다.

## 1. 뭘 하고 있었는지

`codemap-search`에서 사용할 **출처가 명확한 유의어·별칭·약어 사전과 로컬 조회 방식**을 검증하고 있었다.

목표는 다음과 같았다.

- 공개 자료의 의미와 출처를 유지한 JSONL 원본과 조회용 SQLite를 만든다.
- 저장소 단어 빈도는 인덱싱할 때 계산하고, 조회할 때는 기존 사전과 통계만 읽는다. 조회 중에는 모델 호출·네트워크·소스 재탐색을 하지 않는다.
- 실제 코드 저장소에서 유용한 표현이 반환되는지, 다른 의미의 단어가 섞이는지 평가한다.

처음에는 일반 영어까지 포함한 넓은 사전으로 PoC를 완료했다. 이후 잘못된 의미의 후보가 많이 반환되는 문제가 확인되어, **개발 관련 의미와 개별 표기를 선별한 사전으로 다시 평가하는 작업**을 진행했다.

작업은 `apps/codemap-search/experiments/related-terms-poc/` 안의 실험으로 수행했다. 제품 MCP/CLI 통합, 배포용 다운로드 기능, 조회 시점의 LLM 문맥 판정은 구현하지 않았다. 큐레이션과 평가 주석에는 에이전트를 사용했으므로, “조회 중 모델을 사용하지 않는다”와 “작업 전체에서 모델을 사용하지 않았다”는 서로 다르다.

## 2. 과정

| 순서 | 수행한 작업 | 주요 결정과 진행 내용 |
|---|---|---|
| 1 | 원본 사전 구축 | Open English WordNet, GitHub Explore, Wikidata, 두 약어 자료 등 5개 출처를 고정했다. 의미·표기·관계·출처를 보존하는 JSONL과 SQLite를 만들고 무결성 및 상호 변환 결과를 확인했다. |
| 2 | 로컬 조회 구현 | Express·Flask·Gin·Tokio의 고정된 버전을 대상으로 단어별 실제 파일 수를 인덱싱 시점에 저장했다. 조회는 사전 후보에 저장소 존재 여부·빈도·중복·개수 제한을 적용하도록 했다. |
| 3 | 원본 사전 평가 | 입력 92개 × 저장소 4개, 총 368개 조회 결과를 평가했다. 반복 실행과 오프라인 실행도 확인했다. 기술적으로는 동작했지만 다른 의미의 후보가 많아 개발용 정제 필요성이 드러났다. |
| 4 | 개발용 후보 분류 | 7,147개 개념과 그에 속한 17,830개 표기를 검토했다. 단어 철자만 보고 판단하지 않고, 출처에 기록된 의미와 개별 표기를 기준으로 포함·제외·불확실을 구분했다. 나머지 104,571개 개념은 직접 검토하지 않은 기본 제외 영역으로 남겼다. |
| 5 | 독립 의미 검토와 교정 | 276개 개념을 진단 검토한 뒤 사용자 정책에 따라 15개를 수정했다. 이어 위험 조건에 해당하는 299개 개념을 검토해 40개를 추가 수정했다. 총 55개 교정은 별도 이력으로 남기고 원래 판단 기록을 보존했다. |
| 6 | 개발용 사전 생성 | 확정된 개념·표기만으로 새 JSONL/SQLite를 만들었다. 관계도 원래 의미에 속한 양쪽 표기가 모두 유지된 경우에만 남겼다. 두 번의 성공 빌드가 일치했고, 독립 데이터·소비자 검증을 거쳤다. |
| 7 | 기존 사전과 분리해 새 측정 | 원본 사전과 과거 평가를 덮어쓰지 않고 개발용 선택 파일과 고정 평가 프로필을 만들었다. 동일한 92개 입력·4개 저장소·기존 통계로 새 측정을 수행했다. 입력 검증, 출력 경로 보호, 배정 크기 문제를 보완하면서 이전 세대도 보존했다. |
| 8 | 새 의미 라벨 생성·수집 | 기존 의미 라벨을 복사하지 않고 23개 배치에서 159개 라벨을 새로 만들었다. 최종 반환 후보 쌍 97개와 필터 탈락 후보 쌍 62개였다. 실제 읽기·출력·식별자·누락·중복을 검사한 뒤 제출 JSONL로 수집했다. |
| 9 | 최종 독립 검증에서 중단 | 수집과 `labels-check`는 통과했다. 이후 별도 검토자가 보호 파일 상태를 비교하다 `package.json` 행에서 오류를 만났다. 사용자의 “이번에도 오류면 작업 멈춰” 지시에 따라 추가 진단 없이 전체 후속 작업을 중단했다. |

### 개발용 정제에서 적용한 기준

- 코드·시스템 중심으로 판단하되, 직접적인 수치·삼각함수 연산은 포함할 수 있도록 했다.
- 일반적인 참여 활동, 교육·커뮤니티 설명, 범용 계측기 사용만으로는 개발 관련성을 인정하지 않았다.
- 짧거나 드문 표현이라는 이유만으로 제외하지 않았다. 정확한 기술 용어의 풀네임은 설명문이 없어도 의미를 뒷받침할 수 있지만, 모호한 제목에 없는 문맥을 만들어 넣지는 않았다.
- 버전 없는 개념에 특정 버전의 별칭을 섞지 않았다. 숫자가 들어갔다는 이유만으로 모든 이름을 제외한 것은 아니다.
- 불확실한 의미는 조회 대상으로 내보내지 않았다. 출처에 없는 표기·별칭·추론 관계를 추가하지 않았다.
- 새 평가 결과에 맞춰 사전·입력 사례·판정 기준을 튜닝하지 않았고, 새 평가 주석에 과거 라벨을 복사하지 않았다.

## 3. 결과

### 완료된 결과

| 항목 | 결과 |
|---|---|
| 원본 PoC | 사전 구축, 인덱싱 시점 통계, 로컬 조회, 원본 평가 및 보고 완료. 원본 산출물은 보존했다. |
| 개발용 데이터셋 | `rtd1-47baa61927c4b090`: 개념 **3,810개**, 표현 **5,965개**, 의미별 표기 기록 **8,445개**, 관계 **15,578개**, 출처 **5개**. SQLite 약 **9.30 MiB**. |
| 개발용 데이터 검증 | 원본 부분집합 여부, 승인된 교정, 관계의 의미별 연결, SQLite 무결성·구조·JSONL 일치, 네이티브 정규화와 실제 조회를 확인했다. |
| 개발용 선택·측정 | 원본과 별도의 선택 파일 및 고정 프로필을 구성했다. 기존 SQLite·통계·인덱스를 재사용해 **368개 조회 관측, 내부 조회 1,840회**를 실행했다. 이 단계에서 사전·인덱스를 재구축하지 않았다. |
| 기술적 반환 현황 | 입력 **53/92개**가 사전에 등록되어 있었고, **124/368개** 조회에서 최종 후보가 비어 있지 않았다. 이는 등록·반환 여부이며 의미 정확도가 아니다. |
| 새 평가 라벨 | **159개** 생성 및 수집 완료. 기존 라벨을 재사용하지 않았고, 라벨과 근거를 변경하지 않은 채 제출 파일로 옮겼다. |
| 기계적 제출 검증 | 검증 → 수집 → 고정된 평가기의 `labels-check` → 제출 파일 검증이 통과했다. 다만 이 성공이 다음 단계의 독립 인수를 대신하지는 않는다. |

원본 사전 평가에서는 368개 조회 중 **63개(17.1%)**에서 동의어 또는 유사어가 반환되었다. 최종 고유 후보 쌍 317개 중 **141개(44.5%)**는 의도와 다른 의미로 판정되었다. 이 결과가 개발용 정제의 배경이다. 두 비율은 분모가 다르며, 에이전트 주석에 기반한 결과이지 사람의 정답 데이터로 검증한 정확도가 아니다.

**개발용 사전이 원본보다 의미 정확도가 좋아졌다는 결론은 아직 낼 수 없다.** 새 라벨의 최종 독립 인수가 완료되지 않았고, 의미 품질 집계도 실행하지 않았다. 반복 실행 1,840회 역시 독립적인 의미 평가 사례 1,840개를 뜻하지 않는다.

### 끝내지 못한 작업

- 제출된 159개 라벨에 대한 최종 독립 인수.
- 개발용 사전의 동의어·유사어·별칭·약어·잘못된 의미 비율 집계.
- 원본 대비 결과 해석과 최종 보고서·README 결과 갱신.
- 최종 지표와 문서의 독립 검토.

현재는 **작업이 중단된 상태**다. 오류 원인 조사, 재검증, 집계, 후속 실행은 사용자의 새로운 명시적 승인 없이 진행하지 않는다. 이미 생성된 자료를 삭제하거나 되돌리는 작업도 하지 않았다.

## 4. 오류 해결을 위한 과정

아래 복구는 마지막 중단 지시 이전에 승인된 범위에서 수행한 이력이다. 실패 기록을 성공으로 바꾸지 않았고, 개정한 코드와 선택 파일의 이전 버전도 보존했다.

| 문제 | 확인한 원인 또는 범위 | 당시 조치와 결과 |
|---|---|---|
| Python·Rust 정규화 결과 불일치 | 비ASCII 표기의 처리 결과가 서로 달랐다. | 정규화 계약을 수정하고 구세대 자료를 무효화·보존했다. 이후 전체 표현과 표기에 대해 두 구현의 일치를 확인했다. |
| 분류 실행·입력 전달 제약 | 초기 자동 검토 제한, 큰 한 줄 JSON의 읽기 제한, 과도한 배정 자료 등 서로 다른 문제가 있었다. 후반 배정의 예산 초과는 발견했지만 실제 모델 문맥 초과가 발생한 것으로 주장하지 않았다. | 승인된 입력·도구 범위를 명확히 하고, 읽기 가능한 서식과 바이트 기준 배치로 나눴다. 의미 근거를 잘라내지 않고 필요한 자료 전체의 전달을 검사했다. 자동 검토 패키지는 사용자가 제거했다고 알렸으며, 어시스턴트가 보안 설정을 우회한 것은 아니다. |
| 네이티브 결과 파일·출력 전달 실패 | 일부 실행에서 요구된 출력 파일이 없거나 실행 컨텍스트 검증이 실패했다. 출력 값이 보인다는 사실만으로 정식 결과를 인정할 수 없었다. | 실패를 보존하고, 승인된 동일 실행 방식 안에서 재시도했다. 구조화 출력과 정식 게시 결과를 연결하고, 완료된 실행 영수증을 기준으로 결과를 수집하도록 했다. |
| 과거 자료와 새 실행의 식별자 충돌 | 과거 생성기와 현재 검증 도우미를 같은 것으로 비교하거나, 원본 인계 파일을 새 사전으로 바꾸면 재현 근거가 깨지는 문제가 있었다. | 과거 생성기와 현재 도우미를 구분해 기록했다. 원본 인계는 유지하고 개발용 선택 파일·평가 프로필을 별도로 만들었다. 새 산출물의 검증을 거쳐 진행했다. |
