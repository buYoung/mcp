# codemap-search 도입 설계

작성일: 2026-10-17. 상태: 설계(구현 전). 대상 데이터셋: `rts5-75e02862daa29308`(`rt-sense/5`).

관련어 PoC의 뜻 조회를 codemap-search(Rust MCP 서버)에 넣기 위한 설계다. 사용자가 정한 결정을 먼저 적고, 그 결정을 따르는 구조, 구현 순서, 검증 방법을 적는다.

## 결정한 것

| 항목 | 결정 |
| --- | --- |
| 데이터 배포 | 데이터셋을 `tar.zst` 압축 파일로 GitHub 릴리스에 올리고, codemap-search가 내려받는다 |
| 켜고 끄기 | 기본값은 꺼짐이다. 켜야 도구가 목록에 나오고, 그때만 데이터셋을 내려받고 로컬 인덱스와 코드베이스 근거를 만든다 |
| 의존 | 뜻 데이터셋 하나만으로 동작한다. 관련어 데이터셋 `rtr1`(430MiB)과 `rtpoc3`를 쓰지 않는다. Python 코드를 옮기지 않고 Rust로 새로 구현하며, 조회 구조를 처음부터 효율적으로 짠다 |
| 라이선스 | CC BY 등 외부 자료는 배포 데이터에서 모두 뺀다. 외부 사전 자료는 `rtr1`에만 있고, 뜻 데이터셋은 LLM 생성 자료에서 출발했다([데이터셋 생성 과정](pipeline.md)). 따라서 배포하는 것은 뜻 데이터셋뿐이다. 저장소의 기존 PoC 고지 파일과 [원자료](sources.md)의 라이선스 열·문단도 지운다 |
| 데이터 갱신 | 데이터셋 판은 codemap-search 바이너리에 고정한다. codemap-search를 업데이트해도 고정한 데이터셋 id가 같으면 이미 받은 파일을 그대로 쓴다 |
| 도구 형태 | `search`에 섞지 않고 별도 읽기 전용 도구로 넣는다. 식별자 분리는 서버가 하고, 출력에는 상한과 잘림 안내를 둔다 |
| 읽는 방식 | 내려받은 뒤 SQLite 인덱스를 한 번 만들고, 조회할 때마다 SQL로 필요한 행만 찾는다. 시작할 때 전부 메모리에 올리지 않는다 |
| 품질 | codemap-search로 옮긴 뒤 개선한다 |
| 코드베이스 맞춤 | 사전의 관련어 가운데 이 코드베이스에 나오는 단어를 앞세우고, 코드에 근거가 없는 뜻(주제·분야)을 뺀다(사전 ∩ 코드베이스). 새 유의어 발굴은 하지 않는다. 확실한 검증이 필요하고, 브랜치를 바꿀 때마다 갱신한다 |
| 뜻 빼기 기준 | 출발 기준은 "기대 분야 적중이 줄지 않고, 잘못 뺀 비율이 5% 이하"다. 구현한 뒤 측정값을 보고 사용자가 수치를 확정한다 |
| 테스트 | `tests/e2e/`에 계약을 지키는 핵심 테스트만 더한다(7절) |

브리프셋: [`docs/briefs/2026-10-17-briefset-rterms.md`](../briefs/2026-10-17-briefset-rterms.md)

## 1. 전체 구조

```text
GitHub 릴리스: rts5-75e02862daa29308.tar.zst (안에 dataset.sqlite3)
  └─ 내려받기 (기능을 켠 뒤 서버를 시작할 때, 백그라운드)
       └─ ~/.codemap/related-terms/<dataset_id>/dataset.sqlite3   ← 해시 확인 뒤 로컬 인덱스를 만듦. 작업 공간이 같이 씀
작업 공간 색인 (tree-sitter 심볼, 기존 codemap-search 색인)
  └─ 코드베이스 근거: 사전 단어의 등장 횟수 (작업 공간마다, 메모리)
synonyms 도구
  └─ 조회 = 원본 데이터셋(SQL) + 코드베이스 근거로 고르고 줄임 + 출력 상한
```

## 2. 데이터 배포

### 올리는 것
- 릴리스 태그는 바이너리 태그(`codemap-vX.Y.Z`)와 따로 둔다. 예: `related-terms-data-rts5-75e02862daa29308`
- 파일은 `rts5-75e02862daa29308.tar.zst` 하나이고, 안에는 `dataset.sqlite3`만 있다.
- 형식별 크기(31.7MB 파일 기준)는 다음과 같다. `tar.gz`는 압축을 gzip으로 하므로 `.gz`와 크기가 같다.

  | 형식 | 크기 | 필요한 의존성 |
  | --- | ---: | --- |
  | `tar.gz` | 13.24MB | `flate2`를 일반 의존성으로 옮기고 `tar` 추가 |
  | `tar.zst` | 10.41MB(`--ultra -22`), 10.57MB(`-19`) | `tar`만 추가 |
  | `tar.xz` | 9.55MB | `tar`와 새 C 라이브러리(liblzma). 릴리스 대상 8개에서 크로스 빌드 필요 |

- `zstd`는 tantivy(`tantivy-sstable`)를 통해 이미 바이너리에 들어 있다(`cargo tree -i zstd`). 직접 의존성으로 올리고 `tar`만 더한다. `flate2`는 지금처럼 빌드 의존성으로 둔다(`apps/codemap-search/Cargo.toml`의 `[build-dependencies]`).
- 압축을 풀 때는 `dataset.sqlite3` 하나만 받는다. 다른 이름, 절대 경로, `..`가 든 항목은 거부한다.
- codemap-search 바이너리에 데이터셋 id, 내려받을 주소, 압축을 푼 파일의 크기(31,715,328바이트)와 SHA-256(`90b77386962e7037969271f449e8f5253c38059f09bc10c91a415267669f9ced`)을 박는다. 데이터를 바꾸려면 codemap-search를 새로 릴리스한다. 바이너리와 데이터의 판이 늘 맞고, 받은 파일이 맞는지 확인할 수 있다.
- 내려받는 폴더 이름이 데이터셋 id이므로, codemap-search를 업데이트해도 고정한 id가 같으면 이미 받은 파일을 그대로 쓰고 내려받지 않는다. 새 id를 고정한 릴리스만 새 폴더에 내려받는다. 인덱스 판이 바뀐 릴리스는 내려받지 않고 기존 파일에 인덱스만 다시 만든다. 더는 쓰지 않는 이전 판 폴더를 지우는 일은 나중에 정한다.
- 올리기 전에 배포 데이터에 외부 자료가 없는지 확인한다. 뜻 데이터셋에는 뜻풀이 같은 외부 사전 문구 열이 없다. 테이블은 `terms`, `fields`, `topics`, `topic_fields`, `concepts`, `personas`, `input_senses`, `input_relations`, `relations`, `relation_kinds`, `sense_meta`다.

### 내려받기
- 위치는 전역 폴더(`$CODEMAP_HOME`, 없으면 `~/.codemap`, `apps/codemap-search/src/config.rs:105`) 아래 `related-terms/<dataset_id>/`다. 여러 작업 공간이 같은 파일을 쓴다.
- 기능이 꺼져 있으면 내려받지 않는다. 켜져 있으면 서버를 시작할 때 백그라운드에서 받는다. 그동안 도구를 부르면 기다리지 않고 "데이터셋을 내려받는 중"이라고 답한다. `search`가 색인 중일 때 안내를 붙이는 방식과 같다.
- 받은 파일은 임시 이름으로 두었다가, 해시를 확인한 뒤 이름을 바꾼다. 여러 codemap-search 프로세스가 동시에 받지 않도록 프로세스 사이 잠금을 쓴다. 전역 지침 목록이 쓰는 파일 잠금(`apps/codemap-search/src/mcp/global_instructions/registry.rs`의 `lock_registry`, `File::try_lock`)과 같은 방식이다.
- HTTP 클라이언트는 Jev가 쓰는 `reqwest`(rustls)를 다시 쓴다(`apps/codemap-search/src/jev/transport.rs`).
- 받지 못하면 이유와 함께 "사용할 수 없음"을 답하고, 다음 호출에서 다시 시도한다.

### 설정 키
| 키 | 기본값 | 쓰임 |
| --- | --- | --- |
| `related_terms.enabled` | `false` | 켜면 도구를 목록에 넣고, 데이터셋 내려받기·로컬 인덱스·코드베이스 근거 계산을 한다. 끄면 셋 다 하지 않는다 |
| `related_terms.dataset_path` | 없음 | 내려받지 않고 이 파일을 쓴다(오프라인 설치, 개발). `enabled`가 켜져 있을 때만 쓴다 |

키 하나를 더할 때 고칠 곳은 약 9군데다. `config.rs`의 필드·병합·검사, `config/layout.rs`, 영·한 템플릿, `CONFIG_VERSION`과 마이그레이션, 영·한 설정 문서, README다. 문서와 템플릿이 맞는지는 테스트가 확인하지 않으므로 손으로 맞춘다.

README의 "외부 런타임 없음" 문구에 "기본 설정에서는 네트워크를 쓰지 않는다. 관련어 도구를 켜면 데이터셋을 한 번 내려받는다"는 내용을 더한다.

## 3. 로컬 인덱스

`rt-sense/5`는 테이블을 통째로 읽는 조회를 전제로 인덱스를 뺐다([작업 이력 16단계](sense-mapping-log/16-compact-storage.md)). SQL로 필요한 행만 찾으려면 다음 인덱스가 필요하다. 기능이 켜져 있을 때만, 해시를 확인한 직후 한 번, 백그라운드에서 만든다. `dataset_path`로 준 파일은 고치지 않는다. 대신 내려받기 폴더와 다른 `related-terms/local/<dataset_id>/`에 복사본을 만들어 인덱스를 둔다. 복사본의 표시 파일에는 원본 경로, 크기, 수정 시각을 적고, 원본이 바뀌면 다시 복사한다.

여러 프로세스가 같은 파일을 준비할 수 있으므로, 복사부터 표시 파일을 쓰기까지 프로세스 사이 잠금을 잡는다. 복사본은 임시 이름으로 다 만든 뒤 이름을 바꾼다. 조회는 표시 파일이 있는 파일만 연다.

| 인덱스 | 쓰는 곳 | 만드는 시간(측정) |
| --- | --- | --- |
| `relations(word_key)` | 관련어로 이 단어를 가진 단어 찾기 | 0.2초 |
| `relations(persona)` | 다른 단어를 거쳐 읽는 뜻의 직접 관계어 | 미측정. 위와 비슷할 것으로 본다 |
| `personas(topic)` | 같은 주제 단어 | 0.01초 |

이미 있는 키로 충분한 조회는 다음과 같다. 표제어의 관련어(`relations` 기본 키 `term_id`), 입력 단어의 뜻(`input_senses` 기본 키 `word_key`), 개념의 단어(`personas_by_concept`), 단어 찾기(`terms.word_key`).

인덱스를 만들면 파일이 바뀌므로, 해시는 만들기 전에 확인한다. 끝나면 같은 폴더에 데이터셋 id와 인덱스 판을 적은 표시 파일을 둔다. 다음 시작 때는 이 파일만 보고 인덱스가 준비됐는지 판단한다.

## 4. 조회 구현(Rust)

동작 기준은 PoC의 `sense_lookup.py`(`rt-sense-lookup/2`)다. 코드를 옮기지 않고, 같은 결과를 내는 Rust 구현을 데이터셋만으로 새로 짠다.

| 단계 | 내용 | 데이터셋만으로 하는 방법 |
| --- | --- | --- |
| 정규화 | `$state` → `state`, `todo!` → `todo`, 소문자, 단어 사이 구분자 제거로 키를 만든다(`term_canonical.py`의 규칙) | 규칙을 Rust로 구현 |
| 식별자 분리 | `getUserName` → `get user name` | codemap-search의 `split_identifier`(`apps/codemap-search/src/parser/tokenize.rs:3`) |
| 사전 단어 찾기 | 표현 전체 → 기본형(`-s`, `-es`, `-ies`, `-ing`, `-ed`) → 부분 표현 순으로 사전 키와 맞춘다. 자기 뜻이 있는 입력은 기본형으로 넓히지 않는다 | 지금은 `rtr1`의 단어 목록과 맞춘다. 13단계에서는 뜻 데이터셋의 단어에 굴절형 근거가 읽는 영어 굴절형을 더한 `rtr1` 부분집합(263,163개, 41MiB)으로 맞춰도 3,253단어의 결과가 모두 같았다([작업 이력 13단계](sense-mapping-log/13-related-dataset-dependency.md)). 뜻 데이터셋의 단어만으로 맞췄을 때 결과가 같은지는 확인하지 않았다. `blocked`, `retried` 같은 굴절형 입력의 해석이 달라질 수 있으며, 1단계 비교에서 잰다 |
| 기본형 다툼 | 후보 기본형이 여럿이면 데이터 근거로 고른다 | `rtr1`의 관계 대신 뜻 데이터셋 `relations`의 `form` 관계(18,140개)와 굴절형으로 들어오는 관계를 쓴다. 결과가 달라지는 정도는 검증에서 잰다 |
| 표기 별칭 | `polices` → `policies` 같은 확인된 오타 11개(`spelling_aliases.py`의 `CONFIRMED_SPELLINGS`) | 코드 상수로 둔다 |
| 뜻 모으기 | 자기 뜻, 다른 단어를 거쳐 읽는 뜻(`input_senses`), 입력 관계(`input_relations`) | SQL |
| 뜻 정렬 | 검토로만 연결한 뜻은 맨 뒤, 자기 뜻이 먼저, 생성 횟수 순. 횟수가 같으면 주제 단어 수 순 | 1차에서는 벡터 유사도를 쓰지 않는다. 13단계 측정에서 첫 뜻 적중이 1.7%p 내려갔다. 품질 개선 때 작은 벡터를 데이터셋에 넣는 안을 따로 본다 |
| 관련어 모으기 | 직접 관계어, 뜻 미배정 직접 관계어, 가까운 연관어(같은 개념), 같은 주제. 한 번 나온 단어는 다시 쓰지 않는다 | SQL(3절의 인덱스) |

조회 구조는 다음 원칙으로 짠다.
- 시작할 때 아무것도 읽지 않는다. 첫 호출에서 연결을 열고 준비된 문장(prepared statement)을 만든다.
- 한 호출에 들어온 여러 단어는 한 번에 처리하고, 같은 단어는 프로세스 안에서 캐시한다.
- 서버는 요청을 한 줄로 차례대로 처리한다(`apps/codemap-search/src/main.rs:88-93`). 그러니 조회 한 번이 길어지면 안 된다. 단어 하나의 조회 시간을 재서 상한을 정한다.

## 5. MCP 도구

| 항목 | 내용 |
| --- | --- |
| 이름 | `synonyms`. 에이전트 평가에서 쓴 이름이다 |
| 목록 | `related_terms.enabled`가 켜져 있을 때만 `tools/list`에 나온다 |
| 주석 | `readOnlyHint: true`. 다른 도구와 같다(`apps/codemap-search/src/tools/mod.rs`의 `list_tools`) |
| 입력 | `terms`: 문자열 배열. 식별자(`appVersion`)나 여러 단어 표현(`abort signal`)을 그대로 받는다. 서버가 식별자를 나눠 표현 전체와 각 단어를 찾는다 |
| 출력 | 입력마다 해석 결과, 뜻(`분야 — 주제`), 뜻마다 직접 관계어·가까운 연관어·같은 주제. 코드베이스에 있는 단어를 앞에 둔다(6절) |
| 상한 | 뜻 수와 묶음마다 단어 수에 상한을 두고, 자르면 "N개 중 M개"를 적는다. 전체는 클라이언트 상한(기본 100,000바이트, `apps/codemap-search/src/config/output.rs:17-30`)을 넘지 않는다. 처음 값은 뜻 6개, 직접 관계어 20개, 가까운 연관어 10개, 같은 주제 10개로 두고 평가로 정한다 |
| 설명 | 에이전트 평가에서 쓴 `usage-short.md`를 바탕으로 한다. 쓸 때("search keywords, naming")를 구체적으로 적는다. 이를 빼면 호출률이 33~42%로 떨어졌다([에이전트 평가](agent-usage-eval.md)). 식별자 분리는 서버가 하므로 분리 지시는 뺀다 |
| 상태 | 내려받는 중, 사용할 수 없음, 사전에 없음, 코드베이스 근거 준비 중을 구분해 답한다 |

에이전트 평가는 셸 명령이 아니라 MCP 도구로 다시 한다. 호출률, 답에 쓴 출력 비율, 출력 크기를 잰다.

## 6. 코드베이스 맞춤(사전 ∩ 코드베이스)

### 근거 모으기
- codemap-search는 색인할 때 파일마다 심볼 이름과 그 분리 토큰을 모은다(`apps/codemap-search/src/index/engine.rs:914-933`). 색인 결과(`PublishedIndexSnapshot`, `apps/codemap-search/src/index/indexer.rs:81`)의 `ExtractedFile`에서 심볼 이름을 읽는다.
- 이름을 `split_identifier`로 나누고, 이어진 토큰 1~4개를 묶어 키를 만든다. 키 규칙은 단어 사이 구분자를 지우므로 `AbortSignal`, `abort_signal`, `abort signal`이 모두 `abortsignal`이 된다. 이 키 가운데 사전에 있는 것만 센다(파일 수, 등장 수).
- 심볼 쿼리가 데이터 멤버를 심볼로 만들지 않는 TypeScript·JavaScript·C·C++는 필드·속성 시그니처·생성자 매개변수 속성·enum 멤버 이름을 근거 전용으로 따로 모은다. 검색 심볼과 codemap 출력은 바꾸지 않는다.
- 무엇을 근거로 셀지는 검증으로 정한다. 비교할 후보는 세 가지다.
  - 심볼만
  - 심볼과 문서 주석
  - 심볼, 문서 주석, 문자열
- 원본 데이터셋은 고치지 않는다. 근거는 작업 공간마다 메모리에 둔다. 큰 저장소에서 다시 계산하는 시간이 길면 `.codemap/` 아래에 저장한다.
- 첫 색인은 서버 시작과 함께 돌고, 그 뒤의 색인 결과는 바뀐 것이 있을 때만 내놓는다(`apps/codemap-search/src/index/indexer.rs`의 `should_force_publish`). 그래서 데이터셋이 첫 색인보다 늦게 준비되면, 이미 내놓은 최신 색인 결과로 근거를 처음 계산한다. 계산 결과에는 색인 결과의 세대를 붙여, 오래된 결과가 새 결과를 덮지 않게 한다.

### 결과에 반영
- 판단 단위: 출력에서는 한 단어를 한 번만 보여 주므로, 앞 뜻에 나온 단어가 뒤 뜻의 묶음에서 빠진다(`sense_lookup.py`의 `place()`). 그래서 근거 판단은 중복을 빼기 전 뜻마다의 전체 단어로 하고, 중복 빼기와 출력 상한은 그 뒤에 적용한다.
- 관련어: 묶음마다 코드베이스에 있는 단어를 앞에 둔다. 출력 상한에 걸리면 없는 단어부터 잘린다.
- 뜻 뒤로 보내기: 사용자가 기준을 확정하기 전의 기본 동작이다. 근거가 없는 뜻을 근거가 있는 뜻 뒤로 보낸다. 뜻을 빼지는 않지만, 뜻 수 상한에 걸리면 잘리고 잘림 안내에 전체 수가 나온다.
- 뜻의 순서: 입력을 포함한 직접 관련 용어(`bus`의 `event bus`)가 코드에 있는 뜻을 맨 앞에, 입력 자신의 활용형이 아닌 직접·가까운 관련어가 코드에 있는 뜻을 그다음에 둔다. 같은 주제 단어만 코드에 있는 뜻은 순서를 정할 때 근거가 없는 뜻으로 본다. 같은 단계 안에서는 사전 순서를 지킨다. 뜻 빼기는 아래 기준을 그대로 쓴다.
- 부분으로 해석한 구 입력(`measure worker`)은 사전 키가 없어 그 자체로는 근거가 잡히지 않는다. 해석한 부분이 모두 코드에 있으면 입력이 있는 것으로 본다.
- 뜻 빼기: 뜻의 단어(입력 단어 자신은 빼고)가 코드베이스에 하나도 없으면 그 뜻을 뺀다. 측정용 실행에서만 켜고, 사용자가 기준을 확정한 뒤에 기본값으로 켠다.
- 분야 빼기: 코드베이스 전체에서 근거가 하나도 없는 분야는 모든 결과에서 뺀다.
- 거르지 않는 경우:
  - 입력 단어 자체가 코드베이스에 없을 때. 새 이름을 지을 때처럼, 코드에 아직 없는 개념을 찾는 경우다.
  - 걸러서 뜻이 하나도 남지 않을 때. 이때는 거르지 않은 결과를 돌려준다.
  - 근거를 아직 모으지 못했을 때(색인 중).
- 뺀 뜻이 있으면 몇 개를 뺐는지 적는다.

### 갱신(브랜치를 바꿀 때마다)
- 브랜치를 바꾸면 작업 트리의 파일이 바뀌고, codemap-search가 파일 감시나 요청 때 갱신으로 다시 색인한다. 새 색인 결과를 내놓을 때마다 바뀐 파일의 근거만 빼고 더한다. 그래서 브랜치 변경과 파일 수정을 모두 따라간다.
- `synonyms` 도구도 `search`처럼 호출할 때마다 `ensure_alive()`와 `trigger_refresh()`로 갱신을 요청한다(`apps/codemap-search/src/mcp/mod.rs`). 요청 갱신은 감시기가 없거나(`watch = false`), 시작하지 못했거나, 죽었을 때만 실제로 돈다(`apps/codemap-search/src/index/supervisor.rs`의 `trigger_refresh()`).
- `.git/HEAD`를 따로 볼 필요는 없다. 근거는 작업 트리의 내용으로 정해지기 때문이다. 진단용으로 근거를 계산할 때의 브랜치 이름만 기록한다.

### 검증
근거로 쓴 12개 고정 저장소([원자료와 근거 저장소](sources.md))에서 잰다. 평가 세트의 단어는 저장소가 정해져 있다(`sense-eval/eval-set.json`의 `repository`). 각 단어를 그 저장소의 근거로 걸러 조회한다.

2026-10-17 사용자 결정에 따라 **기능 구현을 모두 마친 뒤 Docker에서 새로 clone·index하여 평가한다**. 호스트의 기존 PoC 체크아웃과 인덱스는 사용하지 않는다. 릴리스 게시, 모델을 사용하는 도구 평가와 독립 제거 판정은 보류한다. 판정하지 않은 표본의 오제거율은 0%가 아니라 미평가로 남기며, 제품의 뜻 제거도 계속 끈다.

| 확인 | 통과 조건 |
| --- | --- |
| 맞는 뜻 유지 | 평가 세트에서 기대 분야 적중이 거르기 전보다 줄지 않는다. 출력 상한을 적용하기 전 조회 결과와 실제 도구 응답에서 각각 잰다. 줄어든 단어는 한 건씩 원인을 본다 |
| 뺀 뜻의 정확도 | 뺀 뜻을 저장소마다 20개 이상(적으면 전부) 표본으로 뽑아 두 번 따로 판정하고, 둘이 다르면 한 번 더 판정한다. 그 저장소에서 맞는 뜻을 뺀 비율과, 끝내 갈린 판정을 잘못 뺀 것으로 센 상한을 함께 적는다 |
| 관련어의 쓸모 | 돌려준 관련어 가운데 그 저장소에서 실제로 찾히는 비율이 오른다 |
| 출력 크기 | 거르기 전보다 줄어든 비율을 잰다 |
| 저장소마다 다른지 | 다른 저장소의 근거로 걸렀을 때 맞는 뜻이 더 많이 빠져야 한다. 근거가 저장소를 구분한다는 확인이다. 입력 단어가 두 저장소에 다 있고 예외가 걸리지 않는 경우만 세고, 센 경우와 건너뛴 경우의 수를 적는다. 한 건씩이 아니라 합계로 비교한다 |
| 브랜치 변경 | 한 저장소의 두 판(예: 두 태그)을 오가며, 바꾼 뒤의 근거가 처음부터 계산한 근거와 같은지 본다. 고정 체크아웃 12개는 태그가 하나뿐인 얕은 클론이므로, 따로 받은 임시 클론에서 근거가 서로 다른 두 태그로 한다 |
| 에이전트 평가 | 맞춤을 켜고 끈 두 경우를 MCP 도구로 비교한다 |

맞는 뜻이 줄면 근거로 세는 범위를 바꾸거나, 그 경우는 뜻을 빼지 않고 뒤로 보낸다. 통과할 때까지 뜻 빼기는 켜지 않는다.

출발 기준은 "기대 분야 적중이 하나도 줄지 않고, 뺀 뜻 표본에서 맞는 뜻을 뺀 비율이 5% 이하"다. 구현한 뒤 측정값을 사용자에게 보이고, 사용자가 최종 수치를 정한 뒤에 뜻 빼기를 켠다.

#### Docker 평가 실행

저장소 루트에서 아래 명령을 실행한다. Dockerfile은 현재 작업 트리의 Rust 소스를 `related-terms-eval` 기능으로 빌드한다. 빌드 문맥에는 필요한 소스와 평가 입력만 포함하고, rts5 원본은 컨테이너에 읽기 전용으로 연결한다. Docker 안에서 고정 태그 12개를 얕게 clone하고, 태그와 HEAD의 커밋이 문서의 값과 같은지 검사한다.

호스트와 같은 CPU 아키텍처의 Linux 이미지를 사용한다. 이는 기능 평가이며, 기존 `docker/verify.sh`의 x86_64 배포 호환성 검증을 대신하지 않는다. 인덱스와 체크아웃은 Docker 볼륨에 두고, 측정 결과를 저장소 밖으로 복사한다. Docker 실행에는 호스트 자격 증명이나 Docker 소켓을 전달하지 않는다.

```bash
ROOT="$(pwd)"
RUN_ID="$(date -u +%Y%m%dT%H%M%SZ)"
NAME="rterms-overlay-${RUN_ID}"
OUT="${TMPDIR:-/tmp}/rterms-overlay-${RUN_ID}"
mkdir -p "$OUT"

docker build \
  --file apps/codemap-search/experiments/related-terms-poc/sense-eval/Dockerfile \
  --tag codemap-rterms-eval:local --iidfile "$OUT/image-id.txt" .

docker create --name "$NAME" --init --cpus=4 --memory=6g \
  --mount "type=volume,src=${NAME}-work,dst=/work" \
  --mount "type=bind,src=${ROOT}/apps/codemap-search/experiments/related-terms-poc/datasets/rts5-75e02862daa29308/dataset.sqlite3,dst=/dataset/dataset.sqlite3,readonly" \
  codemap-rterms-eval:local

docker inspect "$NAME" > "$OUT/container.json"
docker start "$NAME"
docker wait "$NAME" | tee "$OUT/exit-code.txt"
docker logs "$NAME" > "$OUT/run.log" 2>&1
docker cp "$NAME:/work/evaluation" "$OUT/evaluation"
docker cp "$NAME:/src/build-info.txt" "$OUT/build-info.txt"
```

`docker wait`가 출력한 컨테이너 종료 코드가 0인지 확인한다. 평가기는 저장소마다 MCP 서버를 시작하고 **초기 인덱스 공개와 최신 근거 준비를 확인한 뒤** 20개 입력을 조회한다. 기존 이벤트 탐색은 기본값인 켜짐을 유지한다. 준비 대기는 저장소별 최대 3,600초이며, 시간 초과와 실패는 `failures`에 남기고 다른 저장소를 계속 평가한다. 미완료 저장소가 있으면 전체 성공으로 보고하지 않는다.

확인할 결과는 다음과 같다.
- `evaluation/report.json`: 12개 저장소 × 3개 근거 범위, 각 범위의 맞춤 끔·뒤로 보내기·제거 모드, 출력 상한 전후 적중, 출력 크기, 실제 코드에 있는 단어 비율, 교차 저장소 대조다.
- `evaluation/repositories/<저장소>/<범위>/removal-sample.json`: 분야와 입력 그룹별 제거 표본이다. 독립 판정은 보류 상태다.
- `evaluation/branch/report.json`: 별도 Express 클론에서 고정 태그와 `4.21.2`(`1faf228935aa0a13111f92c28ee795be64ce3f0f`)를 비교한 결과다. 전환 뒤의 증분 근거와 새로 색인한 근거는 키·파일 수·출현 수까지 같아야 한다.
- `image-id.txt`, `container.json`, `build-info.txt`, `run.log`: 이미지와 자원 제한, 빌드 환경, 실행·실패 기록이다. 큰 원자료는 저장소에 넣지 않고 [통합 기록](integration-log/05-overlay.md)에 결과와 위치만 적는다.

실행이 끝나도 컨테이너와 해당 볼륨은 검토용으로 남긴다. 이전 보고서를 재사용할 때는 `--resume`으로 바이너리·데이터셋·평가 세트·스크립트·저장소 핀의 지문이 같은지 확인한다. 호스트에서 먼저 수행한 측정은 Docker 본 평가의 대체 결과로 세지 않는다.

## 7. 구현 순서

| 순서 | 작업 | 끝났다고 보는 기준 |
| --- | --- | --- |
| 1 | Rust 조회 구현과 로컬 인덱스 준비(로컬 파일 경로로) | 사전 전체 176,351단어를 PoC(`--no-similarity-order`)와 비교한다. 차이는 기본형 근거의 출처 차이로만 설명된다. 그 밖의 차이는 버그로 본다 |

| 4 | `synonyms` 도구, 시작 시 준비, 출력 상한, 도구 설명 | 기능을 끄면 아무 일도 하지 않고, MCP 도구로 다시 한 에이전트 평가 결과가 있다 |
| 5 | 코드베이스 맞춤과 갱신 | 6절 검증 결과를 보고 사용자가 기준을 확정한다 |
| 6 | 품질 개선 | 벡터 축소 재도입, 표제어 표기(K7), 뜻 순서(K9), 기호 입력 잡음([작업 이력 15단계](sense-mapping-log/15-input-inflection-noise.md)) 등 |

테스트는 사용자가 허락한 범위에서 `tests/e2e/`에 더한다. 대상은 계약을 지키는 핵심 동작이다.
- 내려받기가 끊기거나 두 프로세스가 동시에 받을 때 파일이 망가지지 않는다.
- 기능을 끄면 내려받기, 로컬 인덱스, 근거 계산을 하지 않고 도구도 목록에 없다.
- 도구 스키마와 출력 상한.
- 파일이 바뀐 뒤 코드베이스 근거가 갱신된다.

PoC와의 비교와 12개 저장소 검증은 테스트가 아니라 평가 스크립트로 한다.

## 8. 남은 위험
