# Brief Set: 유의어 데이터셋과 로컬 조회 PoC

## Purpose
- Execute phase 1: determine whether a source-grounded dataset can be constructed and whether an actual local lookup returns useful synonyms, with repository word/file statistics produced during indexing rather than during lookup.
- Preserve the user-decided sequence: phase 1 evidence first, contextual LLM judgment second, then a later product-integration experiment. This set implements only phase 1 and records entry conditions for the later phases.
- Coordinate dataset construction, index-time vocabulary/lookup, and independent result aggregation through versioned handoffs. Do not treat the older brief's provisional names, assumptions, observations, or numerical thresholds as established behavior or approval.

- Keep `apps/codemap-search/src/`, main Cargo.toml/Cargo.lock, existing MCP/CLI/config contracts, and `benchmark/` unchanged. A standalone experiment crate may consume public product APIs. If a production edit is genuinely required, return to this parent with evidence instead of making it implicitly.
- Store raw archives, corpora, canonical payloads, SQLite builds, private repository vocabulary, and large traces under ignored `.codemap/poc/related-terms/`. Track scripts, schemas, source locks, attribution, frozen input/review records where safe, compact results, and the three exact handoffs.
- Keep repository-specific words/paths/counts separate from the shareable semantic dataset. Do not publish private source evidence or write it into a future downloadable dataset.
- Compute repository frequency during indexing/finalization and publish it before ready. Serving lookup may only read local semantic data and published statistics: no source walk, reparse, postings enumeration, search-result counting, lazy frequency reconstruction, or network fallback.
- Count unique live indexed files per analyzed word across the selected search fields. Repeated terms and multi-field matches must not double count; deleted documents must not remain. Index and statistics generations and normalization policies must agree.
- Build the repository vocabulary independently of the current dictionary subset. A compatible dataset replacement should not by itself require reparsing the repository. Incompatible normalization/policy versions must be visible rather than silently treated as missing words.
- Preserve phrase/identifier/raw spelling separately from normalized keys. Individual token counts are not phrase occurrence counts. Treat missing, stale, incompatible, unavailable, and genuinely empty states distinctly.
- Preserve source/sense identity and typed evidence. Co-occurrence and repository presence do not prove synonymy; aliases, abbreviations, related-only results, and unverified mined pairs cannot inflate synonym-quality metrics.
- Audit selected Open English WordNet, GitHub Explore, Wikidata structured entities, and the two abbreviation sources at frozen revisions. Do not use CC BY-SA, unlicensed, or license-unverified data, or assume a tool's license covers a separately produced dataset.
- Make canonical record content reproducible and version the normalization/schema independently from dataset content. Keep artifact SHA-256 for integrity distinct from a claim of cross-platform byte-identical SQLite builds.
- Freeze evaluation inputs, intended meanings, review protocol, limits, and filter settings before final observations. Keep development calibration separate. Record the reviewer/labeling method and uncertainty; do not label agent-authored review as independent human annotation.
- The old brief's support count, language/domain minimums, sample count/precision target, 20% filter, 2048-byte block, and top-5 recovery threshold are not inherited user approvals. Settings used in phase 1 must be identified as explicit experiment hypotheses, with actual denominators and limits reported.
- Keep build cost, index-finalization cost, startup/SQLite load, and cold/warm lookup measurements separate. Do not report raw upstream record counts as code-domain coverage, non-empty output as synonym success, or compilation as lifecycle correctness.
- Use existing Cargo checks where applicable and bounded observations for the experiment. Do not add a production unit-test suite, lint/formatter configuration, or generic verification framework. Announce actual verification commands and cwd before execution.

Verify the intended input population is non-empty before accepting no-match/zero-error observations; do not disable protective ignore rules to compensate for an incorrect root.
