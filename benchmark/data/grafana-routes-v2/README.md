# Grafana 기능 경로 3문항 고정 계약

codemap-search 1.0.0 벤치마크용 문항의 개정본이다. 식별자는 `grafana-routes-v2`, 개정 번호는 `2`, 상태는 `content_frozen`이다. 2026-10-03 사용자 개선 요청에 따라 근거와 채점 경계를 보완했다. 현재 작업 트리에는 이 개정만 유지하며 초기 개정은 Git 이력에서 확인할 수 있다. Grafana 기준 소스는 `grafana/grafana`의 `c6fad8695a96577eb466d425e6ac4a759ca30f47`이다.

| 문항 ID | 난도 | 고정 질문 | 필수 핵심 | 확장 진단 |
| --- | --- | --- | ---: | ---: |
| `route-star` | 쉬움 | 대시보드 상단의 즐겨찾기를 추가하거나 해제할 때 화면과 서버가 연결되는 구간 다 확인해줘. | 6 | 2 |
| `route-save-existing` | 보통 | 기존 일반 대시보드를 수정해서 저장할 때 화면과 서버가 연결되는 구간 다 확인해줘. | 7 | 3 |
| `route-live-receive` | 어려움 | TestData의 Grafana Live 스트림을 구독하고 데이터를 받는 구간 다 확인해줘. | 8 | 3 |

세 문항 모두 TypeScript와 Go의 연결을 평가한다. v1의 질문 원문·순서·범위·사실 ID와 핵심 21개·확장 8개 구성을 유지한다. 난도는 정적 경로 구조에 따른 분류이며 실제 LLM 풀이로 검증한 난도는 아니다.

## 개정 내용

| 항목 | 변경 이유와 적용 내용 |
| --- | --- |
| 저장 M2 | 모든 metadata가 최신 serializer 값으로 바뀐다는 오해를 줄이기 위해 저장 시점의 **병합**으로 표현을 고쳤다. 실제 덮어쓰기 우선순위는 비채점 `context_notes`에 기록했다. |
| 저장 M3 | 현재 저장 요청에 필요한 모델 선택·API discovery·beta fallback을 필수로 유지했다. 후속 호출의 재탐색 정책은 비채점 `context_notes`로 분리했다. |
| Live L4·L6 | 필수 경로 설명에서 주의 문구를 분리했다. 네트워크 순서 단정과 HTTP publish 경유 주장은 답변에 실제로 등장할 때 `claim_review_notes`를 참고해 검토한다. |
| 근거 | 저장 클라이언트와 요청 키, 플러그인 지원 확인과 별칭 상수, Live 발행기와 manager 연결, 채널 전달, 수신·응답 생성·구독 정리를 입증하는 13개 구간을 추가했다. 별칭 조회 반환과 discovery의 조건을 포함하도록 기존 2개 구간도 넓혔다. |
| 채점 | 답변의 근거 부족과 평가자의 검증 불가를 구분했다. 사실·차원별 판정을 보존하고 확장 항목만의 오류·보류가 핵심 판정에 전파되지 않도록 명시했다. |

새 근거는 기존 필수 연결의 검증 자료다. 모든 근거 ID나 함수명을 답변에 열거할 의무를 추가하지 않는다. 정답·채점 의미가 달라졌으므로 v1과 v2 결과를 동일한 기준의 점수로 혼합하지 않는다.

`evidence.json`은 원본 81개 파일 전체를 담은 저장소 사본이 아니다. 발췌 원문은 45개 파일의 73개 구간이며 나머지 원본 내용은 파일 메타데이터로만 식별한다.

## 문항 범위

- **즐겨찾기:** 저장된 대시보드의 상단 버튼에서 시작해 요청, 서버 변경, 버튼·메뉴 상태 반영까지 확인한다. 폴더 즐겨찾기나 다른 화면의 진입점을 필수 범위로 넓히지 않는다.
- **저장:** 프로비저닝·Git 관리·템플릿이 아닌 기존 일반 대시보드의 저장을 다룬다. 수정 모델, V1/V2 선택, HTTP 요청, 서버 저장 처리, 응답의 최종 적용을 연결한다. 신규 생성·복사·import·복원은 별도 문항으로 확대하지 않는다.
- **Live:** Grafana Live 편집기에서 선택하는 내장 TestData 랜덤 채널의 구독·생산·수신·정리를 다룬다. 브라우저 생성 스트림, simulation 전용 구현, 사용자 지정 pipeline 상세 처리와 외부 SceneQueryRunner의 패널 렌더링은 필수 범위에 넣지 않는다. 관련 우회 분기는 구분한다.

서버 저장소와 Live 처리 규칙에 따른 조건을 보존한다. 모든 설치가 같은 SQL 저장소를 쓰거나 모든 프레임이 같은 발행 경로를 거친다고 가정하지 않는다. 원문에서 확인한 정적 연결과 실제 서버 실행 관측을 구분한다.

## 채점 계약

각 사실의 `correct`는 설명의 방향·전달값·적용 조건을, `supported`는 답변에 제시한 인용이 그 설명을 입증하는지를 판정한다. 두 차원의 값은 각각 `true`, `false`, `"indeterminate"` 중 하나다. Go와 TypeScript 파일을 각각 찾은 것만으로 연결을 인정하지 않고 URL·식별자·메시지 계약의 대응도 확인한다.

| 상황 | 판정 |
| --- | --- |
| 필수 사실의 미언급·필수 조건 누락·잘못된 연결 | 해당 사실의 `correct=false`. 다른 사실의 판정은 보존한다. |
| 인용 누락·존재하지 않는 위치·해당 사실을 입증하지 못하는 원문 | `supported=false`. 평가 보류로 처리하지 않는다. |
| 평가자의 원문 접근 실패 등으로 필요한 근거를 확인할 수 없음 | 다른 근거로도 확정할 수 없는 해당 사실의 해당 차원만 `indeterminate`와 사유를 기록한다. |
| 확장 항목만의 누락·오류·보류 | 별도 진단으로 남긴다. 핵심 사실 자체의 모순이 확인되면 해당 핵심 사실도 독립적으로 판정한다. |
| 참고 설명·주의 문구의 미언급 | 감점하지 않는다. 실제로 제기한 주장만 원문과 대조한다. |

사실의 두 차원이 모두 `true`이면 충족이다. 하나라도 `false`이면 미충족이며 다른 차원의 보류는 그대로 남긴다. `false` 없이 보류가 남으면 사실 판정을 보류한다. 이에 따라 모든 핵심 사실이 충족이면 `core_complete=true`, 하나라도 미충족이면 `false`, 확정 미충족 없이 보류만 남으면 `"indeterminate"`다.

핵심·확장 및 두 차원의 확정·미충족·보류 수와 사유를 분리해 보고한다. 이미 확인한 실패 때문에 다른 보류를 오답으로 바꾸거나, 보류를 0점으로 채우거나 분모에서 제외한 확정 평균을 보고하지 않는다. 반복 실행의 집계 방식은 별도 실행 계약에서 정한다.

`context_notes`와 `claim_review_notes`는 핵심 21개·확장 8개에 포함하지 않는다. `wrong_claims`와 참고 사항의 문자열 일치로 일괄 감점하지 않는다. 확인된 모순은 영향을 받은 사실에만 귀속하고, 필수 사실과 독립된 추가 주장의 입증 부족은 별도 진단으로 남긴다. 정적 근거로 전달 순서를 입증하지 못했다는 사실만으로 반대 순서가 참이라고 판정하지 않는다. `facts`에 명시된 실제 부정 동작·정리 조건 등 기능 사실의 설명 의무는 유지한다.

풀이 모델에는 `questions.json`의 질문과 동일 조건의 공통 실행 안내만 전달한다. 나머지 파일은 채점·검증용으로 보관하고 풀이 대상 Grafana 작업 공간에 정답 자료를 복사하지 않는다. 대체 인용과 동등한 설명을 허용하며 특정 파일 순서나 탐색 전략을 강제하지 않는다.

## 검증과 보존

내용 고정 시 다운로드한 81개 파일의 원본 바이트를 고정 커밋의 Git tree가 가리키는 blob SHA-1 및 원본 SHA-256과 대조했다. 73개 근거의 행 범위·발췌 원문·해시와 문항별 참조, 핵심·확장 개수, v1 보존 여부도 검증했다. LLM 풀이·채점, 실제 Grafana 서버 시나리오와 난도 실측은 수행하지 않았다.

저장소 루트에서 다음 명령으로 **패키지 파일의 무결성**을 확인한다.

```sh
cd benchmark/data/grafana-routes-v2
shasum -a 256 -c SHA256SUMS
```

이 명령은 고정 파일의 바이트가 기록된 값과 같은지 확인한다. 고정 커밋 원본과의 대조를 새로 수행하는 명령은 아니다. 원본을 재검증하려면 해당 커밋의 소스를 확보해 Git blob SHA-1·원본 SHA-256을 대조하고, 지정한 행 범위에서 발췌 원문을 다시 추출해야 한다.

근거 해시는 원본의 `splitlines()` 결과에서 1-based 양끝 포함 범위를 골라 LF로 결합한 UTF-8 텍스트 기준이다. 결합 후 LF를 추가하지 않으며 마지막 선택 행이 빈 행이면 결합 결과 자체는 LF로 끝날 수 있다. 패키지를 읽고 내부 해시·참조를 검증하는 데 이전 분석의 `/tmp` 파일은 필요하지 않다. manifest의 이전 분석 해시는 출처 식별용이며 해당 분석 파일 전체를 포함한다는 뜻이 아니다.

문항·사실·범위·채점 의미를 바꿀 때는 이 고정본을 덮어쓰지 않고 변경 이유를 기록한 새 개정으로 만든다. 과거 30문항의 결과·점수도 이 세 문항의 기준값으로 재사용하지 않는다.

## 실행기 연결 상태

`grafana-routes-v2`는 현재 단일 벤치마크 데이터셋이다. [실행 계약](../grafana-execution-v1.json)이 3문항 × 6개 비교군 × 1회, 풀이 `gpt-6.1-sol / medium`, 채점 `gpt-6-astra / high`와 도구 기본값을 고정한다. `pnpm bench:ready`와 `pnpm bench:start`는 이 데이터셋을 검증하고 준비만 수행한다.

현재 구현은 `route_contract.py`, `route_grading.py`, `route_metrics.py`와 `route_prepare.py`가 담당한다. 실행·사용량 수집에 필요한 공통 기능도 현재 `benchmark/` 모듈에서 제공한다. 실제 18회 실행 연결은 별도 작업이며 풀이·채점·보정 결과는 아직 없다. 절차와 현재 한계는 [벤치마크 안내](../../README.md), 실제 설치·색인 상태는 [최종 준비 기록](../../../docs/briefs/evidence/bench-ready/07-readiness.json)을 따른다.

`manifest.json`의 `predecessor`와 `execution_contract`는 내용 고정 당시의 출처·연결 상태다. 그 안의 과거 파일 경로는 현재 의존성이 아니며, 초기 데이터셋과 이전 실행기는 작업 트리에서 제거했다. 문항·근거·채점 JSON의 바이트는 유지한다. 운영 안내 README의 변경에 맞춰 manifest의 README 메타데이터와 연결 체크섬을 갱신했으며, manifest에 변경 사유를 기록한다.
