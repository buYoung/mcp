# codemap-search 현재 상태와 후속 보고 형식

기록일: **2026-09-10 (KST)**. 다음 후보 탐색·구현·평가를 시작할 때 이 문서, [보고 기준](REPORTING.md), [기준 등록부](current-baseline.json)를 먼저 읽는다. 사용자의 후속 지시가 우선한다.

## 현재 실행 경로 — Grafana CUI

`pnpm bench:ready`는 고정 Grafana·현재 제품 작업 파일의 release 빌드·색인을 준비한다. `pnpm bench:start`는 Inquirer로 후보 탐색 3문항×3회 / 오류 검증 10문항×1회 / 정식 30문항×2회와 A·현재 버전·등록 후보를 선택한다. 기존 질문 객체의 중첩 부분집합을 고정했으며, 아래 과거 준비 6문항과 구분한다. [현재 사용법과 재개·보존 기준](README.md)을 따른다.

Codex 버전은 고정하지 않고 실제 사용 버전을 기록한다. A 도구 안내·사용량 회수 30초·인용 범위 및 익명화 보완을 공통 코드로 분리했다. 정식 문항의 채점 입력 한도를 지키기 위해 근거·명시 인용 범위와 주변 원문을 전달하며 원래 질문·정답·답변·인용 범위는 바꾸지 않는다. 실제 모델의 새 성능 측정은 이 하네스 구현 작업에서 실행하지 않았다.

과거 결과표와 인과 분석은 당시 작성한 문서 기록이다. 원자료가 없으므로 로그를 새로 대조한 검증 결과로 취급하지 않는다. 고정 A 표·원본 문항과 새 하네스는 유지한다. 과거의 필수 비교 열 A/B-1/B-4/B-6은 당시 보고 계약이며, 새 CUI의 비교 열은 사용자가 선택한 대상이다.

## 정식 평가 대상 — Grafana만

사용자의 최종 정식 벤치 대상은 **Grafana만**이며 비교 대상은 **A와 현재 승인 제품**이다. `pnpm bench:ready`가 Grafana 고정 소스를 준비하는 방향은 이 범위와 맞다. 과거 다중 저장소 결과에 맞추려고 준비 대상을 6개 저장소로 확대하지 않는다. 문항·반복수·실행 계약은 별도 고정하며 이 범위 정정만으로 새 모델 실행을 추가하지 않는다.

아래 `formal-r1-A`의 정답 54/60은 Django·Kubernetes API·Axum·Vite·Gson·fmt의 과거 기록이며 **Grafana 정식 A 기준이 아니다**. 원래 수치와 보류는 보존하되 Grafana 결과표에 대입하지 않는다. 이번 확인에서 최상위 동결 기록의 `formal-r1`은 다중 저장소였고 Grafana `preparation` 3개 차수는 준비 단계였다. Grafana 후보·준비 평가를 완료된 Grafana 정식 결과로 바꾸어 부르지 않는다. 현재 확인 범위에서 완료된 Grafana 전용 정식 A 결과를 찾지 못했다.

## 과거 다중 저장소 보존 참조 — `formal-r1-A`

사용자가 계속 유지하도록 지정한 [A 정식 결과표](results/formal-r1/A.md)와 [60회 원값·출처 해시](results/formal-r1/A.json)를 고정 보존한다. 이후에도 설명 보완 전 A의 과거 실행으로 표시하며, 자동 재측정·재채점하거나 새 결과로 덮어쓰지 않는다. 원래 보류 2회와 도구 안내 오류를 유지한다. 이 보존 요청은 알려진 평가 오류를 없애거나 현재 제품 개선을 확증하는 대조군으로 승인한 뜻이 아니다. 현재 승인된 A 도구 설명과 이 과거 실행의 실제 설명은 별도로 식별한다.

## 현재 제품 반영 상태 — 2026-09-10

현재 소스는 **B-4 + grep/read의 멤버 범위·둘 다 + 하위 폴더 범위 보존·정규식 안내**다. 사용자가 승인한 구성을 `ee1774533`에 반영했고, B-4 기반 파일 4개의 커밋 누락을 `f27ca5edc`에서 복구했다. 현재 제품 소스 기준은 `f27ca5edc1258bcdc4483fda15905bfc96e94a89`, `apps/codemap-search` Git 트리는 `e09df87e2e0c7ff70237475f550cf479eca467ac`이다.

- `grep/read`는 `# symbols`를 먼저, `# results`를 뒤에 출력한다. 같은 파일의 class/struct/impl 멤버와 caller/callee를 제공하며 Go 메서드는 receiver의 struct와 연결한다.
- 범위·안내는 `scope_regex-both`에 대응한다. B-6의 검색 변경, Smart routing, 별도 언어 그룹 패치(`language-both`)와 실험용 환경 변수 분기는 최종 제품에 포함하지 않았다.
- 반영 당시 기존 e2e 47개와 승인된 후보 대비 직접 출력 84건을 확인했다. B-4 기반 커밋 누락 복구 후 관련 기존 e2e 38개, `cargo check`, 커밋 훅의 `cargo fmt --check`·`cargo clippy --all-targets -- -D warnings`가 통과했다. 이것은 구현 검증이며 새 모델 성능 측정이 아니다.
- 로컬 `target/release/codemap-search`는 이번 확인 시 과거 B-4 바이너리 해시 `ee5883514ef219d373adfdf64a453d979f5887fc6841bb3df7fb6405b4430d79`와 같았다. 현재 소스의 빌드·배포 완료 증거로 사용하지 않는다. [기준 등록부](current-baseline.json)는 현재 소스와 과거 측정 바이너리를 구분한다.

이 채택은 사용자의 승인에 따른 결정이다. 아래 단일 Go 문제·5회 결과로 일반적인 정답률·토큰 개선이 확증된 것은 아니다. 과거 결과표의 B-4는 각 실행에 고정된 당시 버전이며 현재 패치 적용본의 새 측정값으로 바꾸지 않는다.

벤치마크 준비 명령(`bench:ready`), 선택형 사용량 수집 보완, 정식 평가 실행기·원본 데이터, 인과 분석·재개 기록을 보존했다. 의미 없는 README 문자열과 IDE의 벤치마크 복제본 매핑, 삭제 대기 중이던 Serena 프로젝트 설정은 정리했다. 사용량 수집에서는 답변 시각이 문자열이 아닌 경우도 시각 확인 실패로 처리해 해당 답변을 제외한다.

## 최신 판단 — 인과 확인과 미확인 범위

**현재 채택 구성은 위와 같다. 안내와 검색식이 도구 선택·목표 코드 노출을 바꾸는 효과는 확인했지만, 사용법 미숙이 높은 전체 토큰과 낮은 정답률의 주원인이라는 가설은 입증하지 못했다.** 도구의 미사용·정보 생성·실제 전달·비용 감소·정답 달성을 서로 같은 효과로 취급하지 않는다. 이전 심볼 실험 `r1`은 사용자가 원한 출력 순서·멤버 계층과 달랐으므로 수정된 `r2`와 구분한다.

### 이전 완료 — 언어·선언별 Smart routing, 새 5회 (`b4-smart-symbols-r1`)

사용자가 요청한 결합 후보를 B-4 기반으로 구현하고 같은 `complex-go-1`에 **새로5회** 측정했다. 기존 멤버 범위+둘 다와 함수 범위+둘 다의 r2 결과는 각5회를 재사용했고 다시 풀거나 채점하지 않았다. **이번 결합은 개선으로 확인되지 않았다.** Smart routing은 정답1/5회·평균 전체 토큰 미확정(≥352,163.2)으로, 기존 멤버 범위의 정답3/5회·319,993.4토큰보다 관측 품질이 낮고 평균 비용은 최소10.0% 높았다. 활성 B-4와 기존 실험은 보존한다.

## `grep/find/read`에 파일별 심볼을 붙이는 시도 이력

2026-09-10 사용자는 자주 쓰는 `grep/find/read` 결과에 파일별 심볼을 추가하는 방향을 제안했고, 우선 과거 시도 확인과 문서 반영을 요청했다. **당시까지 유사한 기능은 있었지만, 반환 파일의 심볼 요약·목록을 세 도구의 응답 자체에 직접 첨부하는 동일한 시도는 확인한 기록에서 찾지 못했다.** 이후 사용자가 `grep/read` 9개 조합의 구현과 45회 실험을 별도로 요청했다. 초기 `b4-live-symbols-r1`과 사용자가 확인한 출력으로 다시 측정한 `b4-live-symbols-r2`를 문서 상단에서 구분해 추적한다. 아래 표는 그 이전 시도 이력이다.

정답 8/10은 A와 R1-C4·R2-C1·R2-C5·R3-C5에서 관측됐다. 하지만 전체 토큰 평균을 확정할 수 없고 모든 후보의 정답 차이 탐색 구간이 0을 포함해 확실한 공동 개선은 확정하지 못했다. **현재 B-4를 유지한다.**

기능 사용도 구분한다. R1-C1의 초기 안내 생략, R1-C4의 symbol 읽기, R1-C5의 value_evidence는 사용 0회다. R2-C5 patterns는 1회 사용했으나 출력 상한 오류로 종료했고, R3-C5 context_lines는 6회/3개 실행에서 사용됐다. 변형 전체의 성과 측정과 특정 기능의 인과 효과 확정은 다르다.

후속 보고는 A/B-1/B-4/B-6 네 열과 6개 필수 행을 유지하고 후보 전체를 오른쪽에 추가한다. 미리 고정한 문항·정답 계약·반복수와 호환되는 기준 결과를 재사용하며, 이 10문제 수치를 다른 구성의 평가에 복사하지 않는다. 새로운 실행은 사용자 요청 범위에서만 한다.

## 현재 제품과 작업 위치

- 채택 제품과 로컬 release 바이너리는 **B-4**다. **B-6은 미채택**이며 결과를 보존한다.
- B-7의 공통 설명 축소는 단일 후보로 구현·12회 사전 검증했으며 전체 15개 평가를 대신하지 않는다. 기존 버전 이름을 재사용하지 않는다.
- 후보 선정·개선 판단에는 **실제 모델의 토큰 사용량과 정답**을 사용한다. CPU·도구 시간·내부 작업량 감소를 이 두 지표의 개선으로 대신하지 않는다.
- 저장소 범위는 **Grafana**다. 앞으로 정식 문항에서 고정 오류 검증 부분집합, 그 안에서 더 작은 고정 후보 탐색 부분집합을 사용한다. 기존 준비 6문제 결과는 과거 진단 기록으로 보존한다. 오류가 있었던 과거 정식 30문제 결과와 다른 저장소 결과는 개선 판정에 사용하지 않는다.

## 보존한 네 버전 사전 검증 질의 재측정

보존한 준비 질문 재측정은 **`grafana-four-way-r1`**이다. A / B-1 / B-4 / B-6을 각각 새 세션 6회, 총 **24회** 실행했다. 이 표에는 과거 실행의 점수를 섞지 않았으며 향후 후보 성능평가의 고정 기준값으로 지정하지 않는다.

전체 사용량은 **22/24회** 확정됐다. A와 B-4는 각 6/6회, B-1과 B-6은 각 5/6회다. B-1·B-6은 복잡한 Go에서 최종 답변 없이 한도 종료됐고 전체 사용량이 불완전하다. `≥`는 기록된 토큰 합을 전체 예정 실행 수 6으로 나눈 **평균 하한**이며 소수 첫째 자리에서 내림했다. 정확한 평균이나 실패 실행을 제외한 평균으로 해석하지 않는다.

정답은 필수 사실과 근거를 모두 충족한 답변이다. 내용이 맞아도 근거가 부족하면 부분 정답이다. 핵심 사실 충족은 맞게 설명한 사실 수를 따로 센다. 따라서 A의 사실 충족 15/15와 정답 4/6은 서로 다른 지표다.

실행 조건은 Codex **0.153.4**, **gpt-5.6-luna medium**, 최대 동시 실행 **2개**, 실행당 **300초 / 80회 탐색 / 캐시 포함 입력+출력 500,000토큰**이었다. 자동 재실행과 추가 채점 모델 호출은 **0회**다. 같은 주 에이전트가 버전 이름을 가린 답변을 고정 원문과 대조했으며 독립적인 블라인드 채점은 아니다.

원자료·판정·보고서 재생성·기존 결과 보존 검증은 통과했다. 수집·집계 검증 통과가 후보 성능평가의 적합성을 뜻하지는 않는다. 이 사전 검증 질의 결과로 후보 우열·채택을 확정하지 않으며, 과거 B-6 비교의 토큰 감소율을 다른 평가에 옮겨 적용하지 않는다.

## 다음 후보에서도 유지할 형식

**후보 탐색 보고, 후보 검증 보고서의 첫 요약, 대화의 최종 결과 답변에 위 표 형식을 그대로 사용한다.** A를 생략하거나 최신 두 버전만 보여주지 않는다. 상세 보고서 링크만으로 이 요약 표를 대신하지 않는다.

1. 기본 비교 열의 순서는 **A / B-1 / B-4 / B-6**이다. 새 후보를 비교할 때는 기존 열을 유지하고 **오른쪽에 후보 열을 추가**한다. 이번 15개는 등록부의 고정 ID를 사용해 누락 없이 표시한다. 여러 표로 나눌 때도 기본 열·여섯 행의 순서를 유지한다.
2. 행의 순서는 **부분 정답 / 정답 / 오답 / 답변 없음 / 핵심 사실 충족 / 평균 토큰 사용량**이다. 총토큰이나 호출 수로 평균 토큰 행을 대체하지 않는다.
3. 고정 평가 계약과 호환되는 기준 결과는 **기존 기록 재사용**으로 표시하고 실행 ID·문항 구성·새 모델 실행 수를 적는다. 호환되지 않는 과거 결과는 별도 표로 보존하고 현재 비교 칸은 미측정으로 둔다. 새 후보의 미측정 칸에 이전 제품 수치를 복사하지 않는다.
4. 실제 검증에서는 각 열의 실행 차수와 **새 실행 / 과거 재사용** 여부를 밝힌다. 같은 버전의 서로 다른 실행에서 유리한 토큰·정답 값을 골라 섞지 않는다. 기준 버전을 자동 재측정하지 않으며, 네 버전 재측정을 명시적으로 요청받으면 별도 차수의 표에 네 버전의 새 실행만 사용하고 기존 표를 보존한다.
5. 평균 토큰은 캐시를 포함한 입력 토큰과 출력 토큰의 합을 전체 예정 실행 수로 나눈다. 캐시를 이중 합산하지 않는다. 전체값이 불완전하면 **미확정**, 함께 제시하는 관측 하한에는 **≥**를 표시한다. 누락을 0으로 채우거나 실패 실행을 분모에서 빼지 않는다.
6. 표 아래에는 정답 정의, 사용량 확정 실행 수, 하한의 의미와 필요한 비교 한계를 적는다. 정답 감소를 토큰 절감으로 상쇄하는 새 종합 점수는 만들지 않는다.
7. 기존 **94개 상세 지표**는 부록·원자료로 유지한다. 후보 선정과 채택 판단에는 토큰·정답을 사용하고, 다른 지표는 원인 분석 자료로 구분한다.

형식을 유지한다는 지시는 모델을 자동으로 추가 실행하거나 정해진 횟수를 늘리라는 뜻이 아니다. 실행 범위·횟수·재실행 제한은 해당 작업에서 승인된 조건을 따른다.

## 기록 갱신과 보존

새 평가를 완료하면 원자료와 보고서를 보존하고 실행 차수별 표·출처를 추가한다. `current-baseline.json`의 최신 관측 참조를 갱신하더라도 고정 비교 기준을 자동으로 대체하지 않는다. 이전 실험의 보고서·점수·해시는 수정하지 않는다. 제품 채택 상태, 고정 비교 기준, 최신 관측 결과를 별도로 기록한다. 기준 변경이나 명시적 재측정에는 새 평가 식별자와 변경 이유를 남긴다.

이 요약은 대용량 `artifacts/` 제외 영역 밖에 보존한다. 새 환경에 원자료가 없다면 이 문서의 기록을 참조할 수 있지만, 원자료 검증이나 새 모델 실행을 했다고 주장하지 않는다.
