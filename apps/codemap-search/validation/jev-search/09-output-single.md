# 검색 출력 개선과 1회 실측 — 2026-09-24

메인 토큰은 **960,703개**로 이전 3회 평균 1,425,426개보다 **32.60% 감소**했다. 같은 입력을 재생한 비교에서도 검색 출력과 `grep` 출력이 줄었다. 다만 이번 답변은 **ServiceCandidate 호출자를 누락**하여 핵심 6/6, 확장 4/5다. 따라서 **출력 절감은 확인했지만 품질 유지까지 달성했다고 수용하지 않는다.**

새 메인 평가 세션은 사용자 지시대로 **#2 조건 1개**다. rg·#11·#13·off 및 이전 결과를 다시 측정하지 않았고 실패 대체나 추가 세션도 없다. 아래 오프라인 비교는 저장된 판정 재생이며 메인 모델·Jev API 호출이 없다.

## 1. 적용한 변경

| 변경 | 동작과 보존 범위 |
| --- | --- |
| 검색 주석 압축 | 비호출 참조의 모든 반환 위치를 파일별 행 목록으로 묶고 반복 소스 조각을 줄인다. 미해석 호출 이름은 모두 유지한 채 목록을 한 줄로 묶는다. 반복 주의문은 처음 한 번 정의하고 뒤에서는 같은 표식을 쓴다. 흔한 이름을 임의로 삭제하거나 확인된 호출 관계를 제거하지 않는다. |

| 전달 예산 연결 | 명시된 `codex_output_token_limit`에 따라 검색 표시 예산을 제한한다. 이번 32,000 설정은 112,000바이트다. 일치·불확실 판정 본문을 우선 보존하고, 넘치는 낮은 우선순위 본문에는 정확한 파일·행 범위의 `read` 안내를 남긴다. 이를 Jev 불일치 판정과 구분한다. |

| webhook 마스킹 | `/hooks/` 뒤의 긴 불투명 토큰과 뒤따르는 경로·질의 문자열을 마스킹한다. 원문 반환과 Jev 요청에서 동일하게 적용된다. |
| 측정 집계 구분 | 이번 실행의 집계기에서 MCP 원본의 생략 안내와 클라이언트에 실제 전달된 생략 안내를 따로 센다. 파일명이 같은 재읽기나 생략 범위와 겹치는 읽기를 곧바로 낭비·복구 비용으로 부르지 않는다. 이전 집계 파일은 수정하지 않았다. |

검색 표시 압축은 **Jev 입력 포착과 판정이 끝난 뒤 표시용 복사본**에 적용한다. 질문·근거 구성·0.70 임계값·연결 보호 정책은 이번 변경에서 유지했다. webhook 마스킹은 Jev 입력에도 적용되는 의도적인 예외다. 평가 대상 파일명이나 정답을 제품 규칙에 넣지 않았다.

112,000바이트는 `32,000 × 3.5`로 잡은 표시 여유 예산이다. 실제 토크나이저의 환산값이나 임의의 다중 도구 묶음 전체에 대한 상한 보장은 아니다. 여러 도구가 한 셀에 같이 출력되거나 보호 본문이 매우 많은 경우의 모든 절단을 없앴다고 주장하지 않는다. 설정을 명시하지 않으면 이 추가 예산은 적용하지 않는다.

- 세 경우 모두 이전에 관측한 클라이언트의 128,000바이트 절단 경계 아래였다. 이 경계는 이번 Codex 버전·설정에서 확인한 값이다.

`grep`은 과거 호출 중 원문 보기·본문 펼침 없음 조건에 해당하는 **64건을 실제 로컬 MCP로 쌍 비교**했다. 총 **3,231행**의 `(파일 경로, 행 번호, 일치/문맥 구분, 원문)`이 동일했다. 출력은 **356,659B → 211,936B, 40.58% 감소**했다. 바이트 감소율이며 메인 토큰 감소율로 직접 치환하지 않는다.

재생 근거: 외부 실행 디렉터리의 `data/offline-validation.json`, `data/anchor-preservation.json`, `capture/priority-{1,2,3}/`. 이전 시도와 최종 재생은 파일을 분리했다.

관측된 메인 감소는 이전 평균 대비 **464,723개, 32.60%**다. 이전 최저값보다도 낮지만, 캐시 미적중 입력은 이전 S1보다 많다. 소요 시간은 이전 평균 276.372초보다 **9.67% 증가**하여 속도 개선은 확인되지 않았다. 로컬 색인 준비 43.160초는 위 평가 시간과 별도로 기록했다.

유지된 #11.1 평균 947,241 및 #13 평균 793,505.67보다 이번 메인 토큰은 여전히 높다. 이번 비교가 원래 전체 수용 조건을 충족했다는 뜻도 아니다. 이 두 기준선은 재실행하지 않았다.

### 실제 적용 확인

- 질문 등록 1회, 검색 1회에서 Jev가 실제 적용됐다. 후보 55개에 대한 질문별 판정 110개가 선별에 소비됐다. HTTP 응답은 7개 모두 사용량을 보고했고 fallback은 0이다.
- `grep` 18회 **전부 `source_grouped`**를 선택했다. `read`는 45회, `find`는 3회였다.
- 첫 검색 원본은 **66,932B**, 이를 포함한 가장 큰 외부 출력 셀은 **71,562B**였다. 외부 출력 절단과 MCP 오류는 모두 0이다.
- Jev 생략 안내는 원본 32개, 실제 전달본 32개다. 표시 예산으로 지연된 본문은 **0개**여서, 이번 실측의 절감 전부를 예산 제한 효과로 설명할 수 없다. 예산 보호 장치의 동작은 앞의 큰 검색 재생으로 확인했다.
- 이번 첫 검색 인자는 `measure worker event bus publish subscribe emit on message` 및 `include_events=true`였다. 이전 세션들과 질의·후속 탐색이 같지 않다.

## 5. 무엇을 효과로 확정할 수 있는가

1. **확정:** 같은 입력·저장 판정에서 표시 바이트가 감소했다. `grep`의 위치·원문은 동일했고, 큰 검색의 클라이언트 절단 경계를 피하면서 기존 채점 근거 행을 유지했다.
2. **관측:** 새 단일 세션의 메인 토큰은 32.60% 낮았다. 요청 수는 15–16회에서 13회로 줄었고, `grep`도 새 형식을 사용했다.
3. **인과 미확정:** 메인 감소율 중 형식 압축, 다른 질의, 후속 호출 수, 덜 완전한 탐색이 각각 차지한 몫은 나눌 수 없다. ServiceCandidate 누락도 있으므로 전부 순수 효율 향상으로 귀속하지 않는다.
4. **미달:** 11개 항목의 품질 유지와 전체 기준선보다 낮은 메인 토큰이라는 기존 수용 조건은 충족하지 않았다. 1회 관측으로 안정적인 절감률도 확정하지 않는다.

남은 품질 개선 지점은 **공유 함수의 외부 호출자 범위 확인**이다. 모든 파일을 넓게 다시 읽게 하는 대신, 확인한 진입점의 호출 위치만 적은 양으로 확보할 수 있는 방법을 검토할 수 있다. 이는 이번에 검증한 제품 변경이나 추가 실행으로 기록하지 않는다.

## 6. 기존 검증과 최종 상태
