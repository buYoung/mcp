# 메인 토큰 증가 원인과 Jev 단독 개선 검증

현재 근거에서 우선 적용할 후보는 **함수 본문·확인된 호출 관계를 보존하면서, 동명이인 참조와 반복 안내를 줄이는 것**이다. 저장된 세 세션에서 첫 검색 응답이 각각 3.30%·26.00%·24.60% 작아졌다. 본문 판정 질문을 강하게 바꾸는 실험은 한 세션에서 응답이 커져 우선 적용안으로 채택하지 않는다.

새 벤치마크용 메인 모델 실행은 0회다. 실제 Jev 검증은 준비한 각 입력을 한 번씩 실행했다. 이후 전체 모델 실측은 사용자 지시에 따라 #2만 단일 세션으로 진행하는 기준이다. 현재 제품 코드를 바꾸거나 전체 토큰 절감을 달성했다고 선언하지 않는다.

## 1. 범위와 판정 기준

- 분석 대상: `20260924-jev-search-quality-04-parallel3`에 저장된 3개 세션. rg·#11·#13·off·#1·#1+#2는 재실행하지 않았다.
- 제품 소스: `54c0f8f5f55b003978a3573c543df92a0a18aef543c42e0b69e5de16330348c3`, 릴리스 바이너리: `505f6b0837c8d8ff791859d09d5fac44196e7fb5305704773df26fc4dac32b5a`.
- 평가 대상: `hicare-rpm-api`, 원래 작업 요청과 소스·설정을 유지했다. 서로 다른 검색어·질문·탐색 경로는 LLM의 정상적인 선택 차이로 취급한다.
- 고정 품질 기준은 핵심 6개·확장 5개다. 이 기준의 설명 포함 여부를 전체 답변의 정답률과 동일시하지 않는다. 기준표는 새 Jev 판정 입력에 넣지 않았다.
- 관측은 저장된 결과, 원인은 소스에서 확인한 발생 구조, 새 질문·출력 실험은 후보 검증으로 구분한다. 전체 모델의 후속 행동은 재현하거나 고정하지 않았다.

## 2. 관측 결과: 어디서 메인 토큰이 커졌는가

메인 합계는 `입력 + 출력`이다. 캐시 입력은 입력의 일부이며, Jev 토큰은 이 표에 포함되지 않는다.

| 세션 | 메인 합계 | 캐시 입력 | 비캐시 입력 | 출력 | 모델 요청 |
|---|---:|---:|---:|---:|---:|
| 1 | 1,304,883 | 1,168,128 | 124,039 | 12,716 | 15 |
| 2 | 1,553,773 | 1,379,200 | 160,753 | 13,820 | 16 |
| 3 | 1,417,622 | 1,247,488 | 156,511 | 13,623 | 15 |

평균은 **1,425,426토큰**이다. 전체의 88.0~89.5%가 캐시 입력이고, 최종 한 요청의 입력은 144,115 / 158,162 / 153,946토큰이었다. 즉 130만~155만 개의 서로 다른 새 자료를 읽은 것이 아니라, 커지는 대화 문맥이 여러 요청의 입력에 누적 계산됐다. 캐시 토큰도 현재 평가 지표인 메인 합계에는 포함된다. 가격·실제 청구액과 혼동하지 않는다.

첫 요청의 22,653토큰을 요청 수만큼 반복하면 339,795 / 362,448 / 339,795토큰이다. 이는 입력 규모의 산술적 분해이며, 그만큼을 실제로 삭제할 수 있다는 뜻은 아니다. 후반 5~6요청에 기록된 토큰은 679,593 / 870,275 / 717,532다. 후반에는 ServiceCandidate 생산자와 조건·오류·계약 근거도 조사했으므로 이 요청들을 불필요하다고 단정하지 않는다.

공개 MCP 응답의 원문 텍스트 양은 다음과 같다. JSON 포장·오류 봉투·메인 입력의 잘림 이후 텍스트와는 다른 바이트 지표다.

| 세션 | search 전체 | read | grep | 전체 도구 텍스트 |
|---|---:|---:|---:|---:|
| 1 | 64,436 | 202,106 | 130,108 | 401,896 |
| 2 | 152,067 | 186,155 | 139,141 | 482,447 |
| 3 | 161,914 | 245,502 | 98,846 | 510,098 |

read·grep가 전체 도구 텍스트의 약 67~83%다. 세션별 read 51/50/50회, grep 29/24/21회였다. 단순 read→read 동일 행 중복은 6/3/3행으로 작았다. 검색·grep까지 포함한 앞선 원문과의 중복 행은 143/586/643행이지만, 2·3번 검색 응답은 메인에 전달될 때 잘렸으므로 그 중복 전체를 불필요한 재독이라고 부를 수 없다.

로거 참조의 발생 지점은 `apps/codemap-search/src/callers/annotate.rs`의 선언 수 검사와 비호출 참조 fallback이다. 선언이 5개 미만이면 fallback이 허용되며, 값 이름이 매우 흔해도 그 빈도만으로는 차단되지 않는다. `info` 변수·`error` 매개변수 등의 문자열 일치가 해당 로거 메서드 참조로 확정된 것은 아니다. 현재 출력에도 approximate라고 표시된다.

반복되는 `Partial source analysis`와 `no direct caller observed` 안내는 불완전성 의미를 보존해야 한다. 동일한 긴 문장을 심볼마다 다시 쓰는 대신, 한 번 정의하고 각 위치에 참조를 남기는 압축은 가능하다.

## 4. 이번 자료로 원인이라고 단정할 수 없는 것

- **Jev에 준 피호출자 원문 자체가 메인 입력으로 복제된다:** 아니다. `supporting_sources`는 Jev 요청 상태에 들어간다. 메인 영향은 최종 본문 보존 결정 등을 통한 간접 효과다.
- **후속 후보 안내가 직접 백만 토큰을 만들었다:** 현재 3회차의 후속 안내는 각각 373 / 1,040 / 1,040바이트다. 이 크기만으로 전체 증가를 설명할 수 없다. 후속 탐색에 미친 영향도 고정된 대조 실험 없이는 분리할 수 없다.
- **경로가 다르거나 read가 많으면 오류다:** 세션별 검색어·질문·경로 차이는 정상적인 변동이다. 확인된 낭비 구조와 별개다.
- **같은 파일을 다시 열면 중복 낭비다:** 대부분 다른 범위였다. read끼리의 동일 행 중복은 전체 3,745~4,831행 중 3~6행이다.
- **오래 조사할수록 정답이 좋아진다:** 3번은 메인 1,417,622토큰을 사용하고도 `manual_extra`를 완전히 연결하지 못했다.
- **현재 품질 개선 전체를 되돌리면 된다:** 저비용 단일 관측은 확장 1/5였고 이번은 5/5·5/5·4/5다. 전면 복구를 품질 보존 해법으로 삼을 근거는 없다.

## 5. 품질 누락의 위치

핵심 기준은 모두 6/6, 확장은 5/5·5/5·4/5다. 빠진 항목은 3번의 수동 입력 `extra` 계약 연결이다.

3번은 도구 11번째 read에서 `measure-worker.persistence.service.ts:210`의 `if (data.extra)`와 검증 이력 저장 호출을 받았다. 생산자 원문도 읽었으며 최종 답변에는 “세 큐 생성 함수가 extra를 넣지 않는다”까지 적었다. 하지만 수신 쪽의 조건부 이력 저장과 연결하는 설명이 빠졌다. 따라서 이 사례의 남은 문제는 **자료 미발견보다 이미 읽은 두 근거의 연결 누락**이다. 재검색량을 늘리는 접근은 우선순위가 낮다.

품질 유지에는 통신 경로뿐 아니라 생산자·소비자 필드 대응, 오류 분기 순서, 커밋 뒤 알림, 우회 경로가 필요하다. 다음 개선에서는 해당 원문을 유지하고, 이미 얻은 근거를 답변에 연결하는 방식을 실험해야 한다. 현재의 최종 점검 안내도 이 항목을 완전히 보장하지 못했다.

## 6. 실제 Jev 단독 검증 방법

1. 저장된 3개 세션의 첫 검색 입력을 현재 제품 라이브러리로 재구성했다. 기존 HTTPS 평가기 경계에 모의 전송을 주입해 **23개 요청 바이트·SHA-256이 원래 요청과 일치**함을 확인했다.
2. 당시 판정을 재생한 검색 출력도 **3/3 완전 일치**했다. 빠진 답변 ID는 0개다. 이것은 네트워크 없는 재생 확인이다.
3. 그 뒤 실제 `jev-1.13.0`을 호출했다. 본문 후보 162개에는 통신 경계·계약의 구체적 정보 기여를 묻는 단일 기준을 적용했다. 이전 여러 질문의 any 판정보다 전이 호출 관계만으로 본문을 유지하지 않도록 작성했다. task·후보 본문·지원 근거는 같은 것으로 유지했다.
4. 2·3번에 공통으로 있던 비호출 참조 301개는 중복을 제거해 한 번 판정했다. 명백한 값·매개변수·다른 필드와 가능한 함수값·callback을 구별하도록 했다. 불확실하면 유지한다. callback 양성 사례 전반의 재현율 검증은 이번 범위에 없다.
5. 각 입력의 실판정은 1회다. 26개 평가 입력이 전송 예산에 따라 HTTP 27회로 나뉘었다. 자동 재시도·대체 판정은 없다. 이 횟수는 전체 모델 벤치마크 27회를 뜻하지 않는다.
6. 새 본문 판정을 기존 보호·관계·본문 렌더링 규칙에 주입해 최종 검색 응답을 재생했다. 본문을 막무가내로 삭제한 숫자를 성과로 쓰지 않았다. 실제 실험용 질문은 변경됐으므로 이전 공급자 판정과의 차이에 확률적 변동이 섞일 수 있다.

실제 사용량은 **입력 436,459 + 출력 9,029 = Jev 445,488토큰**이다. 본문 실험 372,620, 참조 실험 72,868토큰이다. HTTP 모두 200, 사용량 미보고 0, 응답 검증 실패 0이다. 새 벤치마크용 메인 모델 사용량은 없다.

## 7. 개선 후보별 결과

### 후보 A — 본문 보존, 비호출 참조 선별과 반복 안내 압축

Jev는 301개 비호출 참조 중 300개를 제외 후보로, `return this.instance.info` 한 개를 불확실(0.31)로 판정했다. 제외 문턱은 yes≤0.30이며 불확실 항목은 유지했다. callback 가능성을 이유 없이 거짓으로 치환하지 않았고, 생략 개수·불완전성·grep 복구 안내를 남겼다. 반복 안내는 뜻과 적용 위치를 남기는 사전 참조로 바꿨다.

| 세션 | 기존 첫 검색 바이트 | 후보 A 바이트 | 감소 | 본문 코드 블록 |
|---|---:|---:|---:|---|
| 1 | 64,154 | 62,036 | 3.30% | 동일 |
| 2 | 152,067 | 112,533 | 26.00% | 동일 |
| 3 | 161,632 | 121,870 | 24.60% | 동일 |

총 377,853→296,439바이트, **21.55% 감소**다. 1번에는 해당 비호출 참조가 없어 반복 안내 축소만 작용했다. 2·3번에서는 참조 축소가 각각 29,076바이트, 반복 안내 압축이 추가로 10,458 / 10,686바이트를 줄였다. 번호가 있는 원문 행과 코드 블록은 3/3 그대로이며 확인된 호출·이벤트 관계와 후속 후보를 바꾸지 않았다.

이 결과는 원문 증거 보존에 가장 유리하다. 다만 301개가 같은 로거 이름에 집중돼 있어 모든 언어·callback 패턴에 일반화할 수 없다. 매번 301개의 문항을 별도로 추가하면 Jev 비용이 든다. 제품 적용은 우선 반복 안내 압축과 비확정 참조의 별도 출력 예산을 중심으로 설계하고, 의미 선별은 필요한 후보에 한정하는 편이 적절하다. 심볼 수·본문 예산 전체를 줄여서는 안 된다.

### 후보 B — 본문 판정 기준을 통신 경계 중심으로 변경

| 세션 | 기존 첫 검색 바이트 | 후보 B 바이트 | 변화 |
|---|---:|---:|---:|
| 1 | 64,154 | 67,880 | +5.81% |

## 8. 권장 적용 순서와 검증 범위

1. **반복 안내를 한 번 정의하고 필요한 위치에 참조한다.** 불완전·잘림·미확인이라는 의미를 삭제하지 않는다. 본문이 동일한 압축으로 우선 진행할 수 있다.
2. **확인된 호출과 이름만 같은 비호출 참조의 예산을 분리한다.** 확정 관계와 callback 후보·불확실성·복구 경로를 보존한다. 단순 값 이름의 수백 행 확장은 따로 제한한다. Jev 관련성 선별은 이번 실제 결과가 뒷받침하지만 범용 callback 보존에는 추가 설계가 필요하다.
3. **후속 후보에 검증 가능한 소속 함수·읽기 범위를 제공한다.** 위치를 찾기 위한 4~12KB 전체 메서드 목록 조회를 줄일 수 있는 후보이다. 현재 안내는 이름과 파일:행만 제공한다. 효과는 아직 측정하지 않았으며 탐색 순서·횟수를 강제하지 않는다.
4. **이미 읽은 생산자·소비자의 조건부 필드와 오류 분기를 답변에서 연결한다.** 추가 광역 검색을 늘리는 안내보다, 기존 근거 대응을 돕는 작은 출력·답변 구성 실험이 필요하다. 특정 평가 함수명이나 `extra`를 제품 정책에 하드코딩하지 않는다.

Jev의 넉넉한 지원 문맥과 0.70 문턱, 원문 read/grep, 기존 품질 개선은 유지한다. 질문만 좁히는 후보 B는 보류한다. read/grep에 새 Jev 단계를 붙이는 제안은 이번 범위에 포함하지 않는다.
