# 프롬프트 유지보수와 MCP 호출 증가 대응

이 문서는 `codemap-search` 안내문을 압축한 뒤 MCP 호출이 증가하거나 탐색 방식이 달라졌을 때 사용한다. **기능·형식 설명의 중복을 줄이더라도, 각 도구에서 추가 호출을 생략하도록 하는 판단 조건은 보존한다.** 공통 안내에 같은 의미가 남아 있다는 이유만으로 도구별 판단 규칙까지 제거하지 않는다.

서버 안내, 공통 탐색 지침, 도구 설명, 인자 설명, 오류·복구 안내를 변경할 때 함께 참고한다. 특정 프로젝트의 실행 기록이나 결과에 의존하지 않는 유지보수 절차다.

## 1. 적용 범위와 완료 기준

프롬프트 압축의 목적은 **장황한 문구와 중복을 줄이면서 기존 동작과 성능을 유지하는 것**이다. 전체 작업이 더 빨라지거나 총 토큰이 크게 줄어야만 성공하는 작업은 아니다. 일반 코드의 성능 회귀, 캐시, 색인, 출력 처리 최적화는 별도 과제로 분리한다.

변경 전에 답변 품질, MCP 호출 수, 시간, 토큰에 대한 판정 기준을 각각 정한다. 호출 수의 증가율을 제한할지, 양방향 변동을 제한할지도 명시한다. **한 지표의 허용폭을 다른 지표에 그대로 적용하지 않는다.**

```text
변동률(%) = (수정안 평균 MCP 호출 − 기준안 평균 MCP 호출) / 기준안 평균 MCP 호출 × 100
양방향 변동을 평가할 때의 절대 변동률 = abs(변동률)
```

기준안의 호출 수가 0이면 비율을 계산하지 않고 절대 호출 수로 비교한다. 호출 수만 맞추려고 필수 근거를 생략하거나 탐색을 조기에 끝내면 안 된다. 답변의 필수 경로, 출처, 누락 여부도 함께 확인한다. 시간이나 호출 수가 달라졌다면 평균뿐 아니라 개별값과 산포를 확인한다.

예를 들어 허용 기준을 **절대 변동률 5% 미만**으로 정했다면, 정확히 5%인 경우도 실패다. 반올림 전 산술평균으로 계산하고 표시할 때만 반올림한다. 비교 대상은 같은 조건으로 새로 측정한 기준안과 수정안이며, 과거 진단 실험의 평균을 새 기준안 대신 사용하지 않는다. 시간은 실제 증가·감소를 기록하고 별도의 허용 오차를 임의로 만들지 않는다.

## 2. 압축할 설명과 보존할 판단 조건

형식 설명과 행동 조건을 구분한다. 같은 문장이 여러 곳에 있다는 사실만으로 제거 대상을 정하지 않는다.

| 안내의 역할 | 편집 기준 |
|---|---|
| 공통 출력 형식과 용어 | 의미를 보존하면서 공통 안내로 통합할 수 있다. |
| 도구 선택 조건 | 해당 도구를 언제 선택하는지 가까운 위치에서 확인할 수 있어야 한다. |
| 추가 호출을 생략하는 조건 | 현재 근거로 답할 수 있는지, 후속 읽기가 필요한지 판단할 수 있어야 한다. |
| 부분 결과·오류의 복구 조건 | 재시도가 필요한 경우와 이미 전달된 근거를 재사용할 경우를 구분해야 한다. |
| 인자·권한·범위·출력 제한 | 표현을 줄여도 계약과 예외 조건을 바꾸지 않는다. |

공통 안내에 같은 의미가 남아 있더라도 도구별 설명에서 문구를 제거하거나 위치를 바꾸면 실제 행동이 유지되는지 검증한다. 여러 규칙을 묶어 복원한 실험은 그 묶음의 효과를 평가한 것이다. 개별 문장의 효과나 다른 모델·과제로의 일반화는 별도 근거 없이 단정하지 않는다.

현재 구현은 설명을 압축한 구성에 네 가지 도구별 판단 규칙을 함께 둔다. 유지보수할 때는 다음 역할 분담을 유지한다.

- **서버·공통 안내:** `server.md`에는 최초 안내 호출과 마스킹 공지를 두고, 근거 재사용·종료 조건·출력 해석·권한 설명은 `navigation.md`에 모은다.
- **모노레포 안내:** 공통 `navigation.md` 뒤에 `navigation.monorepo.md`의 범위 선택 안내를 덧붙인다. `initial_instructions`, `overview`, `search`의 설명은 각각 하나의 Markdown 파일을 사용한다. 이전의 `initial_instructions.monorepo.md`, `overview.monorepo.md`, `search.monorepo.md`는 통합된 파일이다.
- **도구·인자 설명:** 도구 설명에는 선택 조건과 필요한 출력 설명을, 입력 스키마에는 인자 계약을 둔다. `tools/mod.rs`의 공통 설명 변수는 소스 중복을 줄이지만, 각 도구의 최종 스키마에는 해당 설명이 각각 포함된다. 네 가지 판단 규칙은 각 도구 설명에서도 유지한다.

이 구성의 Rust 변경은 안내문 조립과 출력 문구에 대응한다. 변경 범위를 확인할 때 설명 문자열과 검색·색인·잠금·설정 로직을 구분한다.

## 3. 유지해야 할 네 가지 도구별 규칙

아래는 이 저장소의 도구별 판단 지침이다. 공통 안내와 의미가 일부 겹치는 것은 의도된 배치다. 문구나 위치를 바꾸려면 최종 MCP 응답과 호출 행동을 함께 비교한다.

### grep: 현재 근거가 충분하면 추가 조회 생략

[grep.evidence.md](../src/tools/instructions/tools/grep.evidence.md)

```text
When file/line evidence is sufficient, use it directly; no overview or reread is required.
```

파일·행 근거가 이미 충분할 때 `overview`나 같은 근거의 재독으로 이어지는 것을 막는다.

### search: 현재 결과로 답하고 부족한 구간만 읽기

[search.md](../src/tools/instructions/tools/search.md)

```text
Answer from sufficient source evidence. Read only missing ranges; do not insert overview or reread already visible evidence. Partial output, ambiguity and list-only rows are not complete source evidence.
```

충분한 검색 결과는 직접 사용하되, 부분 출력·모호한 결과·목록만 있는 결과를 완전한 근거로 오인하지 않는다. 호출 감소를 위해 필요한 후속 읽기까지 금지하는 문구로 바꾸지 않는다.

### read: 필요한 근거만 읽고 분석 알림과 소스를 구분

[read.evidence.md](../src/tools/instructions/tools/read.evidence.md)

```text
Read only evidence still needed; a partial analysis notice is not a request to reread the same source.
```

관계 분석이 부분적이라는 알림만으로 이미 전달된 소스를 다시 읽지 않는다. 실제 소스가 잘려 전달되지 않았다면 필요한 구간을 다시 읽는 것은 유효한 복구다.

### overview: 필요한 위치를 알면 바로 읽기

[overview.md](../src/tools/instructions/tools/overview.md)

```text
If grep/search already supplied the needed file and line, use read directly.
```

유효한 파일·행 위치가 있는데 범위 확인을 위한 중간 `overview`를 삽입하지 않는다. 필요한 위치가 아직 없는 경우까지 `overview`를 금지하는 규칙은 아니다.

## 4. 문구를 수정할 때 확인할 연결 경로

| 소스 | 최종 소비 위치 | 유지할 내용 |
|---|---|---|
| [server.md](../src/tools/instructions/server.md) | MCP `initialize.instructions` | 최초 안내 호출과 마스킹 안내 |
| [navigation.md](../src/tools/instructions/navigation.md) | `initial_instructions` 응답 | 공통 흐름, 근거 사용, 종료 조건, 출력 해석 |
| [navigation.monorepo.md](../src/tools/instructions/navigation.monorepo.md) | 모노레포의 공통 안내 확장 | 범위 선택과 이미 제공한 루트 개요의 재사용 |
| [tools 디렉터리](../src/tools/instructions/tools) | `tools/list`의 각 `description` | 도구 선택·추가 호출 판단·도구별 출력 설명 |
| [tools/mod.rs](../src/tools/mod.rs)의 `list_tools` | 실제 도구 설명과 입력 스키마 | 문구 조합, 동적 권한 안내, 인자 계약 |
| [codemap/monorepo.rs](../src/codemap/monorepo.rs)의 `WorkspaceCatalog` 출력 | 모노레포 범위 목록 | 범위·언어 목록을 유지하고, 중복 `Next Step` 안내는 모노레포 공통 안내에 통합 |
| [tools/grep.rs](../src/tools/grep.rs)의 `empty_result_hint` | grep 결과가 없을 때의 안내 | 활성 필터·정규식 안내와 재시도 전 패턴 또는 필터 조정 조건 |
| [mcp/mod.rs](../src/mcp/mod.rs) | JSON-RPC 응답 | 위 내용이 클라이언트에 전달되는 경로 |

`read.evidence.md`와 `grep.evidence.md`는 `list_tools`에서 **동적 파일 접근 권한 안내 뒤에** 붙는다. `search`와 `overview`의 규칙은 각 설명 파일에 포함돼 있다. 문구뿐 아니라 이 조합 순서도 검증 대상이다.

Markdown 파일만 읽고 반영을 판정하지 않는다. `include_str!` 연결과 조합 순서를 확인하고, 빌드된 서버의 응답에서 문구를 확인한다. 인자 이름·필수 여부·기본값·허용값, 읽기 전용 주석, 모노레포 범위, 권한 및 출력 제한은 프롬프트 압축과 구분해 보존한다.

모노레포의 `initial_instructions`는 공통 안내와 모노레포 안내 뒤에 실제 루트 개요를 붙인다. 안내 문자 수를 비교할 때는 고정 문구와 저장소별 범위·통계 출력을 구분하고, 동적 권한과 모노레포 조건도 기록한다.

## 5. 재발하면 확인할 순서

먼저 변경 전후 안내문, 실제 MCP 응답, 실행 식별자, 바이너리 식별값과 설정을 별도의 실험 기록에 보관한다. 진행 중인 측정이 있다면 그 바이너리·안내·설정을 중간에 바꾸지 않는다. 별도의 후보와 결과로 구분한다.

1. **기준안을 고정한다.** 같은 작업의 압축 직전 안내를 기준으로 삼는다. 다른 모델, 코드, 설정, 캐시 상태의 과거 번호와 바로 비교하지 않는다.
2. **호출 증가를 분해한다.** 총 MCP 호출에서 도구별 증감을 계산한다. `read`는 세션별 첫 파일 읽기와 같은 파일의 추가 구간 읽기로 나눈다. 전자는 “이전에 전혀 보지 못한 내용”과 같지 않다.
3. **모델이 실제로 받은 근거를 확인한다.** 서버 원문과 바깥 도구 출력의 잘림을 구분한다. 두 번째 호출 전에 첫 결과의 필요한 부분이 전달됐는지 확인한다.
4. **변경한 문구와 후속 행동을 연결한다.** 어떤 도구 결과 뒤에 불필요한 `overview`, 범위 확대, 재독, 잘못된 재시도가 생겼는지 세션 행과 인수로 기록한다.
5. **확인한 규칙만 복원한 후보를 만든다.** 전체 설명을 원복하기 전에, 영향을 받은 도구의 판단 조건을 짧게 복원한다. 이때 캐시·색인·출력 한도 코드를 함께 바꾸지 않는다.
6. **응답 반영과 행동을 각각 검증한다.** 최종 MCP 설명이 후보와 일치하는지 먼저 확인하고, 그다음 동일 조건의 하네스로 호출 수·시간·답변 범위를 비교한다.

| 관측한 현상 | 먼저 확인할 근거 | 조치 또는 분기 |
|---|---|---|
| 필요한 파일·행을 얻은 뒤 `overview` 증가 | 이전 출력에 유효한 위치가 실제로 있었는가 | 있었다면 도구별 직접 읽기 조건을 복원한다. 없었다면 필요한 범위 탐색으로 분류한다. |
| `read` 증가 | 앞선 출력의 파일·행·내용, 첫 파일 읽기와 추가 구간 비중 | 이미 충분한 근거가 있었다면 근거 재사용·종료 조건을 복원한다. 새 근거가 필요했다면 단순 중복으로 삭제하지 않는다. |
| 같은 요청 재호출 | 첫 결과가 바깥 출력에서 잘렸거나 전달에 실패했는가 | 미전달 결과의 복구는 필요한 호출로 분류한다. 전달된 결과를 불필요하게 재조회한 경우에만 억제 규칙을 검토한다. |
| 무결과·오류 뒤 재시도 증가 | 패턴·필터·인수 오류와 무결과 안내의 변경 | 잘못된 인수 선택을 유도한 설명이나 복구 안내를 좁혀 교정한다. 동일 요청의 무조건 반복으로 해결하지 않는다. |
| 서버 출력은 줄었으나 토큰은 비슷함 | 모델에 전달된 바깥 출력 크기와 요청별 입력 | 그 사실만으로 압축 실패를 판정하지 않는다. 출력 한도를 늘려 맞추지 않는다. |
| 바이너리·캐시·설정도 함께 달라짐 | 실행 manifest와 준비 상태 로그 | 먼저 조건을 분리한다. 프롬프트만의 원인으로 결론 내리지 않는다. |

동일한 요청이라도 첫 결과의 필요한 부분이 전달되지 않았다면 재조회가 정당한 복구일 수 있다. 복구·실패 호출도 총 MCP 호출 수에는 포함하고, 원인 분류를 별도로 남긴다.

## 6. 검증 방법과 결과 기록

### 구현 검증

Rust 연결 부분을 변경한 경우 저장소 루트에서 기존 명령을 실행한다. 이 문서는 새 테스트·린트·서식 설정을 추가하도록 요구하지 않는다.

```sh
cargo check --manifest-path apps/codemap-search/Cargo.toml
cargo test --manifest-path apps/codemap-search/Cargo.toml --test e2e_tests e2e::mcp::
```

그다음 빌드된 서버의 `initialize`, `tools/list`, `initial_instructions`, 변경한 응답 안내를 보관하고 후보와 비교한다. 동일 조건에서 문구·순서·스키마가 일치하는지 확인한다. 모노레포 여부나 동적 권한 값이 다르면 그 차이를 명시하고 해당 조건끼리 비교한다.

**빌드·기존 검증의 통과와 안내 응답의 일치는 구현 반영의 근거다. 새 LLM 세션의 성능이나 답변 품질이 유지됐다는 판정을 대신하지 않는다.**

### 행동 재측정

변경 전후에 다음 조건을 고정한다.

- 평가 대상 리비전과 입력 문장. 공유 가능한 예제나 합성 자료를 우선 사용한다.
- 클라이언트·모델 버전, 생성 설정, 하위 에이전트 사용 여부.
- 도구 구현, 설정, 파일 접근 권한, 인덱스 준비 상태.
- 반복 횟수, 동시 실행 수, 실행 순서와 실패·중단 처리 기준.
- 집계할 작업 구간, 지표와 허용 변동폭.

채택한 기본 설정과 값을 낮춰 본 별도 실험을 구분한다. `read_output_byte_cap`처럼 결과 전달량에 영향을 주는 값은 양쪽에 같은 값을 적용하고, 설정 원문과 해시를 보관한다. 임시로 설정을 바꿨다면 측정 종료 후 원래 값으로 복구됐는지도 확인한다. 실행 명령뿐 아니라 원본 세션에서 실제 입력·모델·추론 강도·하위 에이전트 사용 여부를 대조한다.

원인을 분리할 때는 같은 실행 코드에서 기준 안내, 수정 안내, 의심되는 판단 규칙만 복원한 안내를 비교할 수 있다. 한 번에 여러 변수를 바꾸지 않는다. 문장별 효과를 주장하려면 문장별로 분리한 비교가 필요하다. 다음 두 단계를 별도로 기록한다.

| 단계 | 확인할 대상 | 완료 근거 |
|---|---|---|
| 원인 분리 진단 | 같은 실행 코드에서 안내문만 바꾼 비교 | 복원한 규칙 묶음과 호출 변화의 관측 근거 |
| 제품 구현의 정식 재측정 | 실제 변경 소스로 빌드한 기준안·수정안 바이너리 | 최종 MCP 응답 일치와 동일 조건의 새 세션 집계 |

중계 과정에서 설명문만 바꾼 진단을 했다면 그 결과를 실제 제품 반영으로 간주하지 않는다. 제품 바이너리의 `initialize`, `tools/list`, `initial_instructions` 및 변경한 복구 안내가 평가한 후보와 일치하는지 확인한 뒤 정식 재측정을 진행한다. 사전 응답 확인은 별도 작업 공간에서 수행해 측정 대상의 인덱스를 의도치 않게 예열하지 않는다.

기존 인덱스의 재사용·삭제·예열 정책을 양쪽에 동일하게 적용한다. 디스크 인덱스를 재사용해도 빌드 식별자 등이 달라지면 파생 캐시는 다시 만들어질 수 있으므로, 인덱스 존재만으로 캐시 적중을 판정하지 않는다. 시작 전후 식별값과 준비 로그를 함께 보관한다. 독립 실행의 개별값과 산술평균, 범위·표본 표준편차를 기록한다. 동시 실행한 묶음의 전체 시간을 실행 수로 나누지 않고 각 세션의 지정 작업 구간을 먼저 계산한다.

원인 분리 실험과 정식 전후 측정은 서로 다른 결과로 보관한다. 별도 분석 세션에서 조건별로 지정한 실행 식별자를 집계하고, 분석 세션을 재사용하더라도 각 요청에 집계 대상과 비교 기준을 명시한다. 예를 들어 조건별 3회라면 다음 형식을 사용할 수 있다.

```text
아래 3개 세션 평균으로 <비교안 이름>으로 해줘.
<세션 ID 1>, <세션 ID 2>, <세션 ID 3>
```

각 측정 세션에서는 평가 대상 요청의 시작부터 완료까지를 집계한다. 후속 식별자 조회나 별도 분석·진단 작업의 시간·토큰을 섞지 않는다. 실행 번호를 다시 사용하면 내부 자료 태그와 원본 식별자로 과거 실행과 구별한다.

정해진 반복 실행을 마치면 사전에 정한 기준으로 판정한다. 불리한 결과만 빼거나 같은 조건을 반복해 유리한 평균을 골라내지 않는다. 실패·중단 처리와 재실행 이유도 남긴다. 규칙 복원 후에도 기준을 넘으면 “복원했으니 해결됨”으로 끝내지 말고 다음 관측 근거로 가설을 다시 좁힌다. 새로운 가설이나 변경 없이 반복 실행을 계속하지 않는다.

다음 정보는 접근 범위가 정해진 실험 기록에 남긴다. 원본 로그와 평가 대상의 코드를 공유 문서에 그대로 옮기지 않는다.

| 기록 항목 | 필요한 내용 |
|---|---|
| 변경 식별 | 기준안·수정안 커밋 또는 작업 트리 패치, 바이너리 해시, 실제 안내 응답 |
| 실행 조건 | 대상 리비전, 설정, 모델·강도·CLI, 입력, 동시성·순서, 캐시 준비 상태 |
| 개별 실행 | 실행 식별자, 완료 여부, 시간, 총·도구별 MCP 호출, 토큰, 바깥 출력 잘림 |
| 판단 근거 | 증가한 호출과 직전 출력, 모델에 전달된 근거, 답변의 필수 경로·누락 여부 |
| 결론 | 동일 조건 기준 변화율, 구현 검증과 행동 검증의 구분, 미확인 사항 |

최신 표시표에는 이번 비교안을 표시하되 과거 원본·집계는 보존한다. 작성 중인 분석 로그는 무결성 목록에서 임시 제외할 수 있으며, 이유와 종료 후 등록 책임을 남긴다. 분석이 끝나면 최종 로그·답변을 등록하고 원본 사본, 수치, 파일 해시를 대조한다. 측정 후 커밋할 때도 측정 당시 패치를 보존하고, 커밋할 제품 소스가 측정한 소스와 같은지 확인한다.

완료 보고는 해당 하네스와 반복 횟수의 판정 범위를 명시한다. 호출·시간 기준을 통과했다는 관측을 답변 품질 동등성, 통계적 유의성 또는 개별 문장의 인과 효과까지 검증한 결과로 확대하지 않는다. 품질을 별도로 평가하지 않았다면 그 사실을 남긴다.

## 7. 교정 범위를 멈추거나 되돌릴 기준

복원 후보가 호출 기준이나 필요한 답변 범위를 만족하지 못하면 해당 후보를 완료로 처리하지 않는다. 되돌릴 때는 이번에 바꾼 안내문과 그 연결 부분만 마지막 검증 상태로 복원하고, 동시 작업 중인 다른 코드·설정·기록은 유지한다. 되돌린 뒤에도 실제 MCP 응답을 확인한다.

설명문 외에 입력 계약이 달라졌거나, 조건을 맞춰도 호출 증가를 특정 행동과 연결하지 못하거나, 추가 읽기가 답변 품질에 필요한지 판정할 수 없으면 그 지점에서 원인 확정을 멈춘다. 담당자에게 공유 가능한 변경 차이와 재현 절차, 호출 증가의 근거, 판정이 갈리는 지점을 전달해 다음 확인 범위를 정한다. 근거 없이 성능 코드 수정으로 범위를 넓히지 않는다.

후속 편집에서도 **공통으로 설명할 수 있는 형식 정보**와 **각 도구에서 호출 여부를 결정하는 행동 조건**을 구분한다. 반복 문구를 제거했다는 사실보다, 전달된 안내와 실제 행동이 보존됐는지를 완료 근거로 사용한다.

## 8. 공유 문서와 실험 기록의 분리

공유 저장소에는 재사용할 수 있는 원칙, 절차, 공개 구현의 연결 경로를 남긴다. 프로젝트별 원본과 측정 이력은 접근 범위가 정해진 별도 기록으로 관리한다.

- 개인 계정·절대 경로, 비공개 프로젝트·고객 이름, 실제 질의·실행 식별자를 공유 문서에 넣지 않는다.
- 대상 코드의 파일명·클래스명·메서드명·주석·로그도 비공개 구조를 드러낼 수 있으므로 검토한다. 이름 일부만 바꾸는 것으로 충분하다고 가정하지 않는다.
- 예시는 공개 자료 또는 합성 자료로 작성한다. 실제 측정값처럼 보이는 가상 결과는 만들지 않는다.
- 이 저장소의 구현 참조에는 저장소 내부 상대 링크를 사용한다. 개인 환경의 파일이나 결과 저장 위치를 링크하지 않는다.
- 공개 가능한 실험 결과를 추가할 때도 공개 범위와 재현 조건을 확인하고, 관측 결과·해석·미확인 사항을 구분한다.
