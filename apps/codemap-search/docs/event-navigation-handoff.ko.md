# 범용 이벤트 연결 분석 논의 인계

작성 기준: 2026-09-15, codemap-search 커밋 `b6416baf3`.

다음 세션이 **자동 이벤트 연결 미포착 문제**를 이어서 검토할 수 있도록 사용자 요구, 확인한 근거, 제안과 미결 사항을 보존한 기록이다. 구현 방식은 확정되지 않았으며, 이 문서 작성 중 기능 수정·PoC·새 측정은 수행하지 않았다. 실행 순서나 구현 완료 조건을 지정하는 작업 브리프가 아니다.

## 사용자의 판단과 요청

사용자는 `grep`의 기본 `callable` 확장을 올바른 변경으로 판단했고 커밋을 요청했다. 해당 변경은 `b6416baf3`에 반영됐다. 이벤트 연결 분석의 부족은 이 변경과 별도 문제로 다룬다.

자동 이벤트 연결을 개선하는 방향에 대해서는 사용자가 다음과 같이 말했다.

> rxjs나 특정 라이브러리 의존성에 저격 패치를 하게되면 밑도 끝도 없어져.. 더 좋은 방안이 필요해.

> 1번은 더 깊게 고민하고 안되면 PoC라도 해서 이벤트 측정을 해보는것도 방법이야.

담당 에이전트는 객체·키·콜백의 저장과 호출을 분석하는 공통 기반을 제안했다. 사용자는 이 제안을 구현 설계로 승인한 것이 아니라, **1번 작업을 다른 세션에서 진행하기 위해 내용을 인계해 달라고 요청**했다. 이후 PoC 대상 저장소 네 곳을 지정했으며, 구체적인 분석 범위와 PoC 방식은 미정이다.

미포착 진단 개선, 여러 도구 응답을 합칠 때의 잘림, 최종 답변의 조건 누락은 별도로 논의한 2~4번 항목이다. 이 문서에는 1번과 혼동하지 않는 데 필요한 사실만 남긴다.


```text
[No eligible event endpoints in this bounded indexed scope. Unknown/unconfigured API receivers are not joined by method spelling.]
```

뒤이어 입력 2개가 unavailable/capped 상태라는 집계도 있었다. 이 집계만으로 해당 두 입력이 미포착의 원인이라고 확정할 수는 없다. 근거는 [#6 도구 응답 기록](/tmp/measure-worker-session-analysis/H-tool-outputs-readable.txt)의 `LINE 75`, 파일 내 1721~1727행이다.

비교 답변들은 `grep`·`read`로 원문을 대조해 다음 통신 경로를 설명했다.


이는 저장된 코드 분석 답변의 내용이다. 실제 런타임 전달을 검증한 결과가 아니다. 자동 맵이 연결을 제공하지 못했다는 사실은 확인했지만, 입력 수집·객체 해석·API 식별·키 해석·연결·출력 중 정확히 어느 단계에서 해당 경로가 빠졌는지는 아직 재현해 분리하지 않았다.

## 논의된 공통 분석 방향 — 검증 전 제안

에이전트가 제안한 방향은 **객체의 생성·전달, 키의 전달, 콜백의 저장·조회·호출**을 공통 사실로 분석하는 것이다. 함수 이름에 `on`, `emit`, `subscribe`가 포함되는지만으로 연결하지 않는다.

설명에 사용한 단순화 예시는 다음과 같다. `refreshCache`와 `change`의 정의는 생략했으며, 실행한 PoC나 회사 코드의 복사본이 아니다.

```js
const registry = {};

function keep(key, callback) {
  registry[key] = callback;
}

function deliver(key, payload) {
  registry[key]?.(payload);
}

keep("cache.changed", refreshCache);
deliver("cache.changed", change);
```

여기서 분석하려는 근거는 `keep`에 전달한 함수가 특정 객체의 키에 저장되고, `deliver`가 같은 객체의 같은 키에서 값을 읽어 함수로 호출한다는 사실이다. 이 사실을 함수별로 재사용할 수 있게 표현하면 이름 변경·별칭·래퍼에도 같은 원리를 적용할 가능성이 있다.

이 예시만으로 분석 방법이 완성된 것은 아니다. 객체 덮어쓰기, 키 변경, 등록 삭제, 조건부 실행, 등록·발행 순서, 여러 인스턴스의 구분을 함께 고려해야 한다. 콜백 저장과 호출이 발견됐다는 이유만으로 모든 컬렉션을 이벤트버스로 분류하거나 실행을 보장해서는 안 된다.

`this.service.eventBus`도 같은 관점에서 검토한다. 필드 이름이나 서비스 타입이 같다는 것만으로 합치지 않고, 생성자 인자·필드 대입·별칭을 거쳐 전달된 객체가 같은지 근거를 확인하는 문제다. 실행 시 구성되는 의존성 주입이나 팩터리 반환값까지 자동으로 해결된다고 가정하지 않는다.

### 외부 구현과 프로세스 경계

공통 분석도 함수 구현을 볼 수 없으면 전달받은 콜백을 저장하는지, 즉시 호출하는지, 버리는지 알 수 없다. 외부 라이브러리 구현을 어디까지 분석할지와 분석할 수 없는 호출을 어떻게 다룰지는 미정이다. 현재 의존성·생성 파일 제외 규칙을 전부 해제하는 방안은 제안되거나 승인되지 않았다.

Redis 같은 외부 통신은 같은 프로세스의 객체 동일성과 별도 문제다. 같은 채널 문자열만으로 서로 다른 서버·환경·클라이언트가 연결된다고 확정할 수 없다. 프로세스 내부 콜백 경로를 개선한 결과를 곧바로 `worker → Redis → API → WebSocket` 전체 경로의 증명으로 확대하지 않는다.

실행 관측을 보조 근거로 사용하는 PoC도 가능성으로 언급됐다. 격리된 실행에서 실제 등록·발행·호출을 관측하면 정적 후보와 비교할 수 있지만, 관측은 실행한 시나리오만 증명한다. 정적 탐색 도구에 사용자 프로그램 실행을 기본 동작으로 넣자는 제안은 아니다.

## PoC 대상 저장소

사용자가 지정한 대상은 다음 네 곳이다.

- LiveStore
- Bevy
- Kubernetes/client-go
- vendure

네 저장소에서 공통 분석의 적용 가능성과 한계를 비교한다는 범위로 인계한다. 저장소별 API 이름을 추가하는 방식으로 기존의 범용성 요구를 대체하지 않는다.

이 문서 갱신에서는 대상 저장소를 탐색하거나 PoC를 실행하지 않았다. 저장소별 기준 커밋, 이벤트 관련 소스 경로, 측정 질의와 정답 연결은 아직 정하지 않았다. 이전 회사 저장소의 #2·#5·#6 결과는 배경 자료로 유지하며 네 저장소의 검증 결과로 취급하지 않는다.

| 같은 키를 쓰는 다른 버스 | 키 문자열이 같아도 객체가 다르면 잘못 연결하지 않는가? |
| 조건·등록 변경 | 콜백 덮어쓰기·제거·조건부 등록 때문에 미확정인 부분을 확정 연결로 표시하지 않는가? |
| 이벤트를 거치지 않는 수신 처리 | 캐시 갱신 같은 직접 처리 분기를 이벤트버스 경로로 오연결하지 않는가? |
| 외부 함수·동적 구성 | 구현이나 객체 연결을 확인할 수 없을 때 근거 없이 호출 대상을 만들지 않는가? |
| 실제 사용 패턴 | 작은 예제에서의 성공이 래퍼·필드·여러 파일을 포함한 실제 패턴에서도 유지되는가? |

PoC 결과에는 정답으로 대조 가능한 연결 중 찾은 수, 잘못 연결한 수, 미확정으로 남긴 수를 분리해 볼 필요가 있다는 취지다. 근거는 소스 대조와 실행 관측을 구분하고, 실행 관측에서 보지 못한 연결을 곧바로 없는 연결로 처리하지 않는다.

실용성은 연결 정확도뿐 아니라 분석 시간·메모리·출력량·추가 조회량과 함께 판단해야 한다. 함수 전체를 많이 반환한 것과 자동 연결이 개선된 것을 구분한다. 전체 모델 세션을 새로 측정하게 되면, 사용자의 앞선 제한인 **측정마다 분석하지 않고 모든 측정이 끝난 뒤 한 번 종합 분석**하는 방식을 유지한다.

## 기존 탐색 기능과의 관계

사용자는 원문을 문장으로 반복하는 `Value relationships`를 불필요하다고 판단해 제외를 요청했다. 이 결정은 `701f3004b`에 반영됐으며, `debug:true`에서도 다시 켜지지 않는다. 공통 분석을 검토한다는 이유로 이 출력을 복원하는 것은 요청 범위가 아니다. 현재 계약은 [값 관계 출력 제외 문서](./value-navigation.ko.md)에 있다.

[flow/mod.rs](../src/flow/mod.rs)의 추출·저장 자료와 신선도 해시는 남아 있다. 평가·렌더링 모듈은 `#[cfg(test)]`로 제한돼 탐색 요청에서 실행하지 않는다. 이전 구현을 재사용할 수 있는지는 검토 후보일 뿐이며, 현재 이미 범용 이벤트 분석이 동작한다고 간주하거나 요청 시 평가를 그대로 되살리는 근거로 삼지 않는다.

논의된 출력 방향은 파일·함수를 넘는 등록·발행·수신 연결과 그 근거 위치를 제공하는 것이다. 동작을 다시 풀어 쓰는 원문 요약을 늘리는 방향은 권하지 않았지만, 구체적인 표시 형식·확실성 분류·공통 분석 결과 구조는 아직 정하지 않았다.

기존 사용자 요구에 따라 이벤트 정보는 `grep/read`의 조회 근거와 관련될 때 자동으로 나타나고, 관련이 없으면 나타나지 않아야 한다. 새 명령어나 매번 추가 옵션을 요구하는 방식을 확정한 적은 없다. 현재 `include_events=false`와 명시적인 이벤트 비활성화 설정은 사용자 선택으로 유지된다.

`grep`의 기본 `expand="callable"`, 명시적인 `expand="none"`, `read`의 기본 줄 범위, 선언 종류·이름별 구획, 파일당 하나의 `results`, 원문 보존은 이미 별도로 확정된 계약이다. 이벤트 분석 논의가 이를 다시 변경하는 요청은 아니다.

## 아직 정하지 않은 사항

- 공통 분석이 처음 다룰 언어·문법·객체 전달 범위와, 지원 언어 전체로 확장할 때 재사용할 경계.
- 외부 의존성의 소스·함수 요약을 확보하는 방식과 분석 범위. 기존 규칙과 공통 분석의 역할 분담.
- 지정한 네 저장소의 기준 커밋·이벤트 관련 소스·측정 질의·정답 연결. 정적 PoC만으로 판단할지, 격리된 실행 관측을 보조로 사용할지.
- 미확정 객체·키·핸들러가 남을 때 연결 결과의 확실성을 표현하는 기준과, 근거 없는 연결을 막을 방법.
- 이전 `flow` 구현의 재사용 가능성, 분석을 색인 시점과 질의 시점에 어떻게 나눌지, 기존 예산 안에서 실용적인지.

위 사항은 다음 세션의 검토 대상이다. 이 기록을 확정 설계나 실행 승인으로 대신하지 않는다.
