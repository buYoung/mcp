This page defines every column, breakdown, and statistical test reported in [Results](/benchmarks/results/).

## Accuracy and fact-grading metrics

Each answer is graded by `gpt-6-astra` (`high`, no tools or repository access) against `12` required facts (`108` across `9` answers, or `84` across `7` answers for `zvec-grep 0.2.2` in `pi codemode`).

| Column | Definition |
| --- | --- |
| `Fulfilled` | Primary accuracy score. A fact counts as fulfilled only when the explanation is accurate (`correct=true`) **and** proven by `path:start-end` line ranges cited in the answer (`supported=true`). All tools—including `rg 15.2.0`—received the identical line-range citation instruction. |
| `Fulfilled %` | Percentage of graded facts marked `Fulfilled` (`Fulfilled / total graded facts`). |
| `Core` | Essential end-to-end hops from entry point to handler or storage: `7` per question (`63` across `9` answers, `49` across `7` answers). |
| `Extended` | Secondary branches, configuration guards, or conditional behaviors: `5` per question (`45` across `9` answers, `35` across `7` answers). |
| `All-core (7/7)` | Count of answers that fulfilled all `7` `Core` facts without missing a link (out of `9`, or `7` for `zvec-grep 0.2.2` in `pi codemode`). |
| `Factually correct` | Facts where the model's explanation was accurate (`correct=true`), regardless of whether the cited line ranges established it (`Fulfilled + Correct, weak citation`). |
| `Correct, weak citation` | Facts where the model described the right behavior, but the cited line ranges failed to establish that claim (`correct=true, supported=false`). |
| `Incorrect / missed` | Equals `total graded facts − Factually correct` (`108 − Factually correct`, or `84 − Factually correct` at `n = 7`). Thus `Fulfilled + Correct, weak citation + Incorrect / missed = total graded facts` (for example, `96 + 2 + 10 = 108`). |
| `Cited test/gen` | Count of answers in that cell citing at least one test or generated file (`Answers citing test/generated files`). |

## Token and turn metrics

Multi-turn coding agents re-send prior conversation context on every turn, so `~86–94%` (`85.9%–94.3%`) of input tokens are served from prompt cache.

| Column | Definition |
| --- | --- |
| `Total tokens` (`mean`, `Median`, `Min–Max`) | All input tokens (cached + uncached) plus output tokens per answer. |
| `Input tokens (mean)` | Mean total input tokens per answer (`Cached input + Uncached input`). |
| `Cached input (mean, %)` | Mean prompt-cache-hit input tokens per answer, with percentage computed across the cell (`sum(cached) / sum(input)`). |
| `Uncached input (mean)` | Mean cache-miss input tokens per answer. |
| `Output tokens (mean)` | Mean tokens generated by the solver model per answer. |
| `Uncached total (mean)` | Mean `Uncached input + Output tokens` per answer, separating newly processed tokens from re-sent cached prefixes. |
| `Turns (mean, min–max)` | Mean, minimum, and maximum model turns taken per answer. |

`Codex code mode` total tokens run `~1.4–1.9×` higher than `pi` largely because Codex includes a larger per-turn developer, tool, and code-mode preamble (for example, `9,748` first-turn input tokens on `codemap-search` versus `5,118` in `pi direct` and `4,338` in `pi codemode`) that is re-sent and mostly cached on every turn.

## Tool-call outcomes and subtool breakdown

| Column | Definition |
| --- | --- |
| `Total calls / ans` | Mean calls per answer, where `Total calls = Dispatched + Rejected`. |
| `Dispatched / ans` | Mean calls per answer actually executed by an MCP tool, built-in tool, or read-only shell. |
| `Rejected (sum)` | Total calls across the cell blocked before execution by the benchmark's read-only path sandbox (such as targeting `.git` or a path outside the source checkout). |
| `Errors (sum)` | Total dispatched calls (`Errors ⊂ Dispatched`) that returned an error (such as a nonexistent path or failing query). |
| `Built-in / fallback` (`Built-in / shell / ans`) | Mean calls per answer to client built-in tools (`read`, `grep`, `find`, `ls` in `pi`) or read-only shell (`exec_command` in `Codex code mode`). `0.0` indicates every run completed using only the MCP server's own tools (`codemap-search 0.14.2` bundles `read`, `grep`, and `find` inside the MCP server). For `rg 15.2.0` (which has no MCP server), this column equals all built-in or shell calls. |
| `Per-subtool calls / ans` | Per-answer call means broken down by individual MCP tool, built-in tool, or shell. |
| `helper read` (`Graphify 0.9.95`) | Read-only MCP `read` helper attached exclusively for `Graphify 0.9.95` because its 7 native graph tools return entities and locations without raw source bodies. Tracked separately from client built-in/shell fallback calls. `zvec-grep 0.2.2` did not receive a `read` helper because `zvec_grep_search` already returns bounded source snippets alongside matches. |

## Citation format and answer length

Citation metrics are recomputed directly from the normalized review citation index (line-range citations extracted uniformly from final answer text) across all `160` eligible answers.

| Column | Definition |
| --- | --- |
| `Range citations / ans (sum)` | Mean per answer (and cell total) of multi-line `path:start-end` citations where `end > start`. |
| `Mean lines / range` | Average line span across multi-line range citations. |
| `Single-line / ans (sum)` | Mean per answer (and cell total) of single-line citations (`path:line` or `start == end`). |
| `Mean answer chars` | Mean character length of the final solver answers in that cell. |

## Client output caps and truncations

| Column | Definition |
| --- | --- |
| `Built-in/CLI cap hits (answers)` | Total cap hits (and number of answers affected) on client limits: in `pi`, built-in `read` (`2,000` lines / `50 KiB`), `grep` (`100` matches), `find` (`1,000` entries), and `ls` (`500` entries); in `Codex code mode`, `Codex CLI 0.164.0` `Warning: truncated output` events across both shell `exec_command` calls and `exec` code-mode cells (which default to a `10,000`-token output cap unless overridden via `// @exec: {"max_output_tokens": ...}`). |
| `Script truncations` | In `pi codemode`, count of `codemode` QuickJS script responses clipped at the extension's `10,000`-token default cap (`—` in `pi direct` and `Codex code mode`). |
| `Adapter truncations` | In `pi`, count of individual MCP tool responses clipped by `@buyong/pi-mcp-adapter 0.1.2` (`20 KiB` default unless overridden by `_meta["pi/maxOutputBytes"]`, which `codemap-search 0.14.2` sets to `100,000` bytes; `—` in `Codex code mode`). |

## Question breakdowns and per-fact matrix

- **Repetition breakdown (`Run 1 · Run 2 · Run 3 (Core+Ext)`)**: Shows fulfilled facts for each of the three runs, followed by `(Core+Extended)` in parentheses—for example, `10 (6+4)` means `10` fulfilled facts (`6` Core + `4` Extended).
- **Per-fact matrix (`A1–AE5`, `G1–GE5`, `B1–BE5`)**: Opaque rubric item IDs represent individual facts (`7` Core IDs numbered `1–7`, `5` Extended IDs numbered `E1–E5`) while keeping paths, symbols, and rubric text private. Each cell lists fulfilled runs in `pi direct · pi codemode · Codex code mode` order (each out of `3` runs, or `v/d` such as `1/1` or `0/1` for `zvec-grep 0.2.2` on `B*`/`BE*` where `2` of `3` `pi codemode` runs crashed), followed by the total across environments (`sum/9`, or `sum/7` for `zvec-grep 0.2.2` on `B*`/`BE*`).

## Statistical test and token ratios

- **Question-stratified exact permutation test**: Pairwise `p`-values use an exact question-stratified permutation test (`8,000` permutations for `9 vs 9`, `1,600` permutations for `7 vs 9`). Reported `p`-values are unadjusted across `24` external-MCP comparisons (`27` total pairwise rows), with `p < 0.05` used as the unadjusted comparison threshold.
- **`Two-sided p` vs `One-sided p`**: `Two-sided p` tests whether the two tools differ in either direction. `One-sided p` tests whether the first tool (`A` in `A − B`) fulfilled strictly more facts per answer than the second (`B`), which is why negative differences yield one-sided `p`-values near `1.0`.
- **Sample resolution at `n = 9`**: With `9` answers per cell (`7` for `zvec-grep 0.2.2` in `pi codemode`), differences of roughly `1.0+` facts per answer are separable, whereas `0.3–0.8` gaps fall within run-to-run noise.
- **`Total token ratio` and `Uncached token ratio`**: Computed by dividing the first tool's mean tokens (`A`) by the second tool's mean tokens (`B`), printed as `×1.71`, `×0.55`, and so on.
